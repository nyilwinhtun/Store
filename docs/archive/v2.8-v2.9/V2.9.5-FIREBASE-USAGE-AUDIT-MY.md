# Minimart v2.9.4 Firebase Usage Audit နှင့် v2.9.5 ပြင်ဆင်ချက်

## အနှစ်ချုပ်

ပေးထားသော v2.9.4 ZIP ကို Source Code အဆင့်တွင် စစ်ဆေးခဲ့သည်။ Firebase Console Screenshot တွင် Last 24 hours အတွက် Reads 81K၊ Writes 27K၊ Deletes 226 နှင့် 2 PM–3 PM ဝန်းကျင်တွင် Reads 54K၊ Writes 15K ခန့် ပြထားသည်။ ဤကိန်းဂဏန်းများကို Source Code တစ်ခုတည်းဖြင့် ဘယ် Collection က ဘယ်လောက်ဖြစ်စေသည်ဟု တိတိကျကျ ခွဲမရပါ။ Firestore Usage Insights / Cloud Monitoring မှ Collection/Operation အလိုက် စစ်ဆေးရန် လိုအပ်သည်။

သို့သော် Source တွင် Read/Write များစေနိုင်သော ဖွဲ့စည်းပုံဆိုင်ရာ အကြောင်းရင်းများကို အတည်ပြုတွေ့ရှိခဲ့သည်။

## A. v2.9.4 Source မှ အတည်ပြုတွေ့ရှိချက်များ

### 1. Realtime Listener အများအပြား

- Branch တစ်ခုစီအတွက် `branchRecordKinds` Collection 15 ခုလုံးကို `onSnapshot()` ဖြင့် Full Collection Listener ဖွင့်ထားသည်။
- Branch List 1 ခု၊ Meta Settings 1 ခု၊ Shared Customer/Supplier 2 ခု ထပ်ရှိသည်။
- ထို့ကြောင့် Branch တစ်ခုတွင် active listener subscription 19 ခု၊ Branch နှစ်ခုတွင် 34 ခု၊ Branch သုံးခုတွင် 49 ခု ဖြစ်နိုင်သည်။
- Listener အများအပြားရှိခြင်းတစ်ခုတည်းက တစ်စက္ကန့်တိုင်း Read ဖြစ်သည်ဟု မဆိုလိုပါ။ Query စတင်ချိန်၊ Document ထည့်/ပြင်/ဖျက်ချိန်နှင့် Reconnect ချိန်များတွင် Read ဖြစ်နိုင်သည်။

### 2. History Collection များကို အပြည့်နားထောင်ခြင်း

Sales၊ Purchases၊ Expenses၊ Payments၊ Stock Transfers၊ Cash Movements နှင့် Activity Logs အပါအဝင် History Collection များကို Cursor/Pagination မပါဘဲ Full Collection Query ဖြင့် နားထောင်ထားသည်။ Record များလာသည့်အခါ Initial Snapshot နှင့် Reconnect ပြန်လုပ်ရာတွင် အဟောင်း Record များပါ ပြန်ဖတ်ရနိုင်သည်။

### 3. Manual Sync သည် Full Cloud Scan ဖြစ်ခဲ့ခြင်း

`CloudSyncPanel.tsx` မှ `readBusinessCloud()` သည် `getDocsFromServer()` ဖြင့် Branch List နှင့် Branch တစ်ခုချင်းစီ၏ Collection 15 ခု၊ Shared Customer/Supplier နှင့် Meta Settings တို့ကို အပြည့်ပြန်ဖတ်ခဲ့သည်။ Manual Sync/Download/Upload လုပ်ဆောင်ချက်များက ထို Full Scan ကို ထပ်မံခေါ်နိုင်ခဲ့သည်။

### 4. Device အသစ် Bootstrap တွင် ထပ်ဖတ်နိုင်ခြင်း

Device အသစ် Bootstrap လုပ်စဉ် Cloud Full Scan ပြီးနောက် တူညီသော Collection များအတွက် Realtime Listener Initial Snapshot ထပ်ရရှိသည့် လမ်းကြောင်း ရှိခဲ့သည်။ ထို့ကြောင့် အလားတူ Data ကို နှစ်ကြိမ်ဖတ်နိုင်သည့် အန္တရာယ်ရှိသည်။ Device/Origin အသစ်တွင် Baseline မရှိလျှင် အချက်အလက်အားလုံးကို တစ်ကြိမ်ဖတ်ရန် လိုအပ်ဆဲဖြစ်သော်လည်း v2.9.5 မှာ Listener Snapshot ရရှိပြီးသားကို Bootstrap အတွက် ပြန်သုံးထားသည်။

### 5. Branch ပြောင်းလဲမှုကြောင့် Listener များ ပြန်ဖွင့်ခြင်း

Branch List ပြောင်းလဲသည့်အခါ ယခင်လမ်းကြောင်းတွင် Branch Listener များကို အများအပြား ပြန်တည်ဆောက်နိုင်သည်။ v2.9.5 မှာ Branch အသစ်/ဖျက်သည့်အခါ သက်ဆိုင်ရာ Branch Listener များကိုသာ ဖွင့်/ပိတ်သည်။

### 6. မတူသော Origin များက Firebase Project တစ်ခုတည်းကို သုံးခြင်း

`localhost:5173`, `localhost:5174` နှင့် GitHub Production သည် Browser Origin မတူပါ။ သို့သော် Config တူလျှင် `store-mini` Project တစ်ခုတည်းသို့ ချိတ်နိုင်ပြီး Origin တစ်ခုစီက ကိုယ်ပိုင် Listener Set ဖွင့်နိုင်သည်။ စမ်းသပ်ချိန်တွင် တစ်ပြိုင်နက် အများအပြားမဖွင့်ရန် လိုအပ်သည်။

## B. Writes 27K အတွက် ဘာကို အတည်ပြုနိုင်သလဲ?

- Sync Write Path `writeItemsIfBaselineUnchanged()` သည် Candidate Record တစ်ခုချင်းစီအတွက် Transaction Read လုပ်ပြီး Remote Hash နှင့် Baseline ကို စစ်သည်။ Hash တူလျှင် Write မလုပ်ပါ။ Conflict ဖြစ်နိုင်လျှင် Write ကို ရပ်ထားသည်။
- Transaction Read သည် Read အသုံးပြုမှု ဖြစ်ပြီး Write မဟုတ်ပါ။
- Initial Bootstrap တွင် Cloud မရှိသေးသော Local-only Record များကို Upload လုပ်ရနိုင်သည်။ Data အများအပြားရှိသော Device/Origin အသစ်များတွင် Write အများအပြား ဖြစ်နိုင်သည်။
- Sale တစ်ခုမှာ Sale Record၊ Product/Batch Stock Update၊ Activity Log နှင့် Credit/Payment Record စသည်တို့ ပြောင်းလဲနိုင်သဖြင့် Business Logic အရ Write တစ်ခုထက်ပို ဖြစ်နိုင်သည်။
- Source တွင် အချိန်တိုင်း `setDoc()` လုပ်နေသော ရိုးရိုး Periodic Write Loop ကို မတွေ့ခဲ့ပါ။
- 15K Writes တစ်နာရီ Spike ကို Source တစ်ခုတည်းဖြင့် အတည်ပြုမရပါ။ Repeated Bootstrap၊ Local-only data upload၊ တခြား App Origin/Version များနှင့် ပုံမှန် Sales/Stock Operations တို့ကို Usage Insights မှ ခွဲစစ်ရန် လိုအပ်သည်။

## C. v2.9.5 တွင် ပြင်ဆင်ထားသည်များ

1. Branch တစ်ခု/Collection တစ်ခုအတွက် တစ်ကြိမ်တည်း Active Listener ရှိစေရန် Map Key Guard ထည့်ထားသည်။ Shared Collection များအတွက်လည်း Guard ထည့်ထားသည်။
2. Product၊ Category၊ Stock Batch ကဲ့သို့ POS ချက်ချင်းလိုအပ်သော Collection များကို Realtime ထားသည်။
3. Sales၊ Purchases၊ Expenses၊ Payments၊ Stock Transfers၊ Cash Movements၊ Activity Logs နှင့် Shared Customer/Supplier များကို `updatedAt` Cursor အခြေခံ Delta Query ပြောင်းထားသည်။
4. Cursor သည် ISO Date String ဖြစ်ပြီး 2-minute overlap သုံးထားသည်။ v2.9.4 Baseline ရှိပြီး Cursor မရှိသေးသော Device များတွင် Manifest `savedAt` ကို စတင် Cursor အဖြစ် သုံးသည်။
5. Device အသစ် Bootstrap သည် Listener Server Snapshot ကို ပြန်သုံးပြီး တူညီသော Collection များကို `getDocsFromServer()` ဖြင့် ထပ် Full Scan မလုပ်တော့ပါ။ Device အသစ်/Origin အသစ်တွင် Baseline မရှိပါက တစ်ကြိမ် Full Initial Snapshot လိုအပ်နေဆဲဖြစ်သည်။
6. Manual Sync ကို လက်ရှိ Listener/Delta Snapshot နှင့် Local Data ကို Reconcile လုပ်စေပြီး Full Cloud Scan လမ်းကြောင်းကို UI မှ ဖယ်ရှားထားသည်။
7. Branch အသစ်/ဖျက်ခြင်းတွင် သက်ဆိုင်ရာ Branch Listener များကိုသာ ပြောင်းလဲသည်။
8. ပုံမှန် Tab ပြောင်းတိုင်း Listener များကို မဖြုတ်/မပြန်ချိတ်တော့ပါ။ Offline/Online ပြန်ချိတ်ချိန် သို့မဟုတ် Background 25 မိနစ်နှင့်အထက်ကြာမှ Delta Listener များကို Cursor အသစ်ဖြင့် ပြန်ချိတ်သည်။
9. Business Data ပြောင်းလဲမှသာ Reconcile schedule လုပ်သည်။ Cart typing၊ Active Tab/Branch UI state စသည့် UI-only state ပြောင်းလဲမှုများကို Sync မလုပ်စေပါ။
10. Write Path တွင် Transaction conflict protection ကို မဖယ်ရှားထားပါ။ အဲဒါကို ဖြုတ်လိုက်လျှင် Device နှစ်ခုက တစ်ပြိုင်နက် ပြင်ဆင်သော Data ကို မတော်တဆ အစားထိုးနိုင်သည်။
11. `[Minimart Sync Listener Plan]`, `[Minimart Sync Snapshot]`, `[Minimart Sync Reconcile]`, `[Minimart Sync Write]` Count-only Diagnostics များကို Browser Console ထဲ ထုတ်ပေးသည်။ Firebase ထဲသို့ Diagnostics Write မလုပ်ပါ။
12. Auto Sync Provider နှင့် Access Bootstrap ကို React StrictMode အပြင်ဘက်ထားပြီး Development Effect Replay ကြောင့် Side-effect Listener မလိုအပ်ဘဲ ထပ်ဖွင့်နိုင်ခြေကို လျှော့ထားသည်။

## D. အရေးကြီးသော ကန့်သတ်ချက်များ / သတိပြုရန်

- v2.9.5 သည် Branch တစ်ခုအတွက် Listener Subscription 19 ခုကို 1 ခုအထိ လျှော့ချထားခြင်း မဟုတ်ပါ။ သီးခြား Collection များအတွက် Listener တစ်ခုစီရှိနေဆဲဖြစ်ပြီး History Query များ၏ ပြန်ဖတ်ရမည့် Document အရေအတွက်ကို Cursor ဖြင့် လျှော့ချထားခြင်းဖြစ်သည်။
- Device အသစ်/Origin အသစ်မှာ Baseline မရှိလျှင် Full Initial Bootstrap တစ်ကြိမ် လိုအပ်နေဆဲဖြစ်သည်။
- Delta Query သည် App ကရေးသားသည့် `updatedAt` ISO String ကို အခြေခံသည်။ Firestore Console သို့မဟုတ် အခြား Tool က `updatedAt` မထည့်ဘဲ ပြင်ထားသော Document များသည် Cursor Query မှ လွတ်နိုင်သည်။ Normal App Flow တွင် Tombstone + `updatedAt` ကို သုံးရမည်။
- Client Clock အလွန်ကွာခြားပါက Cursor အခြေခံ Delta Query မှ Record လွတ်နိုင်ခြေရှိသည်။ Device Date/Time ကို Automatic ထားပါ။
- Transaction Retry ဖြစ်ပါက Browser Console ၏ `transactionReadDocsPerAttempt` ထက် အမှန်တကယ် Reads ပိုများနိုင်သည်။
- Cashier Cloud Sales / Server-side Stock Transaction သည် ဒီ Version တွင် မပါဝင်သေးပါ။
- Firebase Real Project Usage ကို ဒီ Environment မှ တိုက်ရိုက်တိုင်းတာ၍ မရပါ။ 81K Reads/27K Writes ကို v2.9.5 ဖြင့် ဘယ်လောက်လျော့မည်ဆိုသည့် အတိအကျအာမခံ မပေးနိုင်ပါ။ Deploy ပြီးနောက် တူညီသော Device/လုပ်ဆောင်ချက်အခြေအနေဖြင့် Usage ကို ပြန်တိုင်းတာရမည်။
