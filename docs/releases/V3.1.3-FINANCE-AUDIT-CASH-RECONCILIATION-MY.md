# Minimart POS v3.1.3 — Finance Audit & Cash Reconciliation

## ရည်ရွယ်ချက်

Branch တစ်ခုချင်းစီရဲ့ Cash နဲ့ Branch KPay လက်ကျန်ကို App Ledger က မျှော်မှန်းထားတဲ့ပမာဏနဲ့ လက်တွေ့ရေတွက်/စစ်ဆေးထားတဲ့ပမာဏ နှိုင်းယှဉ်နိုင်ရန်၊ Cash Shift ပိတ်သိမ်းမှုမှာ ဘယ်သူဖွင့်/ပိတ်ခဲ့သလဲ သိနိုင်ရန်၊ စာရင်းတိုက်စစ် Snapshot များကို ပြန်မပြင်နိုင်သော Audit History အဖြစ် သိမ်းရန် ဖြစ်သည်။

## ထည့်သွင်းထားသော လုပ်ဆောင်ချက်များ

### 1. Daily Cash / KPay Reconciliation

- Owner က Branch တစ်ခုချင်းစီအလိုက် စာရင်းတိုက်စစ်မည့် Business Date ရွေးနိုင်သည်။
- App Ledger မှ ယနေ့အထိ (သို့မဟုတ် ရွေးထားသောရက်အထိ) မျှော်မှန်း Cash / KPay လက်ကျန်၊ စုစုပေါင်း In / Out ကို တွက်ပြသည်။
- Owner က တကယ်ရေတွက်ထားသော Cash နှင့် KPay App တွင်မြင်ရသော လက်ကျန်ကို ကိုယ်တိုင်ဖြည့်သည်။
- ကွာဟချက်ကို `Actual - Expected` ဖြင့် တွက်သည်။
- ကွာဟချက်ရှိပါက မှတ်ချက်/အကြောင်းပြချက် ဖြည့်ရန် လိုအပ်သည်။
- KPay Account မသတ်မှတ်ထားသော Branch တွင် Cash တစ်မျိုးတည်းကိုသာ တိုက်စစ်နိုင်သည်။
- Snapshot သိမ်းခြင်းသည် Ledger Balance ကို မတိုး/မလျှော့ပါ။ ကွာဟချက်ကို အလိုအလျောက် ညှိနှိုင်းမပေးပါ။

### 2. Append-only Reconciliation Audit History

- `branchFinanceReconciliations` တွင် Branch, Business Date, Channel, Expected, Actual, Variance, In, Out, Note, Created By UID/Name နှင့် Created At ကို သိမ်းသည်။
- Owner သာ ဖတ်ရှုနိုင်သည်။
- Firestore Rules အရ Owner က Create လုပ်နိုင်သော်လည်း Update/Delete မလုပ်နိုင်ပါ။
- တစ်နေ့တည်းတွင် ပြန်လည်တိုက်စစ်ပါက အဟောင်းကို မပြင်ဘဲ Snapshot အသစ်အဖြစ် ထပ်သိမ်းသည်။
- Audit History ကို CSV ထုတ်ယူနိုင်သည်။

### 3. Cash Shift Audit

- Shift ဖွင့်သူ၏ UID/အမည်၊ ပိတ်သူ၏ UID/အမည်ကို သိမ်းသည်။
- Shift Closing မှာ System Expected Cash, Actual Counted Cash, Variance ကို သိမ်းသည်။
- Shift History ဇယားမှာ Opened By / Closed By ကို တကယ်ပြသသည်။
- Manual Cash In/Out တွင် မှတ်တမ်းတင်သူ UID/အမည်ကို ထည့်သည်။
- Cashier Settlement နှင့် Cash Advance Return မှ ဖန်တီးသော Cash Movement တွင် သိရှိနိုင်သော ပေးချေသူ UID/အမည်ကို ဆက်သိမ်းသည်။
- ရှေးအဟောင်း Record တွင် actor field မရှိနိုင်သောကြောင့် UI တွင် `—` ပြနိုင်သည်။

### 4. Cash Advance Return — Double-counting ကာကွယ်မှု

- Cash Advance ပေးချိန်ကို Cash/KPay Outflow အဖြစ် တစ်ကြိမ်သာ တွက်သည်။
- Advance နဲ့ ချိတ်ထားသော Expense သည် Advance ထဲက သုံးစွဲမှုဖြစ်သောကြောင့် Branch Ledger Outflow ကို ထပ်မတိုးစေပါ။
- Cash Advance ကျန်ငွေကို Cash ဖြင့် ပြန်အပ်ပြီး Open Cash Shift ရှိလျှင် Shift Cash In Movement တစ်ခု ဖန်တီးသည်။
- ထို Movement တွင် `sourceSettlementId` ချိတ်ထားသဖြင့် Branch Finance Ledger က Movement ကို ထပ်မတွက်ဘဲ Advance Return Reconciliation ကိုသာ အသုံးပြုသည်။
- KPay ဖြင့် ပြန်အပ်ပါက KPay Transaction ID လိုအပ်ပြီး KPay Ledger Inflow အဖြစ် တစ်ကြိမ်သာ တွက်သည်။

### 5. Local Business Date

- Ledger စတင်ရက်နှင့် Reconciliation Date ကို Device ရဲ့ Local Calendar Date အလိုက် နှိုင်းယှဉ်သည်။
- Ledger စတင်ရက်ကို အနာဂတ်နေ့အဖြစ် သတ်မှတ်မရပါ။
- Reconciliation Date ကို Ledger စတင်ရက်မှ ယနေ့အထိသာ ရွေးနိုင်သည်။

### 6. Cloud Sync

Owner Auto Sync ရဲ့ Local Change Watcher ထဲတွင် အောက်ပါ Finance State များ ပါဝင်သည်။

- `branchFinanceLedgerEntries`
- `cashierAdvanceReconciliations`
- `branchFinanceReconciliations`
- `cashShifts`
- `cashMovements`

အဆိုပါ Record များ ပြောင်းလဲလျှင် Owner Auto Sync က Branch Cloud Collection သို့ Sync စတင်စေသည်။ Historical Finance Collections များကို Incremental Sync ပုံစံအတိုင်း ဆက်ထိန်းထားသည်။

## မပြောင်းလဲထားသော အရေးကြီးအစိတ်အပိုင်းများ

- Firebase Authentication / Owner Login / Cashier Login
- POS Checkout, Product, Barcode, Sales
- Branch Stock, Stock Transfer, Branch Shipment / Receiving / Owner Approval
- Cashier Expense Reporting — Owner Approval မလိုသော တင်ပြပုံစံ
- Cashier KPay Settlement
- Branch KPay Account Settings
- Offline Queue / Existing Cloud Sync Flow

## သတိပြုရန်

- KPay လက်ကျန်ကို App က KPay API မှ အလိုအလျောက်ဖတ်ခြင်း မဟုတ်ပါ။ Owner က KPay App တွင်မြင်ရသော လက်ကျန်ကို ကိုယ်တိုင်ဖြည့်ပြီး တိုက်စစ်ရသည်။
- Reconciliation Snapshot သည် Audit Record သာဖြစ်ပြီး Ledger Entry မဟုတ်ပါ။ ကွာဟချက်ကို ညှိလိုပါက အကြောင်းရင်းစစ်ဆေးပြီး သီးခြားမှန်ကန်သော Ledger Entry တစ်ခု ထည့်ရမည်။
- Full Typecheck, Production Build နှင့် Firebase Real Device Test မပြီးမချင်း Production အသုံးမပြုပါနှင့်။
