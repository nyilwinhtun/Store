# Minimart v2.9.5 — Cloud Sync Efficiency Upgrade

## ဒီ Version ရဲ့ ရည်ရွယ်ချက်

v2.9.4 Source ကို စစ်ဆေးရာမှာ Firebase Read များစေတဲ့ အကြောင်းရင်းအဓိကတွေက Collection တစ်ခုလုံးကို အမြဲ `onSnapshot()` နားထောင်ခြင်း၊ Manual Sync တစ်ကြိမ်နှိပ်တိုင်း `getDocsFromServer()` Full Scan ပြန်လုပ်ခြင်း၊ Device အသစ်မှာ Full Scan ပြီးပြီးချင်း Listener Initial Snapshot ထပ်ဖတ်ခြင်းတို့ ဖြစ်နိုင်ကြောင်း တွေ့ရှိခဲ့ပါတယ်။

v2.9.5 မှာ အောက်ပါအတိုင်း ပြင်ဆင်ထားပါတယ်။

## 1. Realtime နှင့် Incremental Listener ခွဲခြားခြင်း

**POS ချက်ချင်းလိုအပ်တဲ့ Collection များကို Realtime ဆက်ထားသည်။**

- categories
- products
- stockBatches
- branches
- meta/settings

**History / ပြောင်းလဲမှုနည်းသော Collection များကို `updatedAt` Cursor ဖြင့် Incremental Query ပြောင်းထားသည်။**

- sales
- expenses
- heldItems
- customerPayments
- purchases
- supplierPayments
- purchaseReturns
- stockReceipts
- stockTransfers
- cashShifts
- cashMovements
- activityLogs
- shared customers / suppliers

ဤနည်းလမ်းသည် Historical Collection အားလုံးကို App ဖွင့်တိုင်း အပြည့်ပြန်ဖတ်ခြင်းကို လျှော့ချရန် ဖြစ်သည်။ `updatedAt` ကို ISO UTC string အဖြစ် သိမ်းထားတဲ့ လက်ရှိ Data Structure နဲ့ ကိုက်ညီအောင် `where(updatedAt >= cursor - 2 minutes)` သုံးထားသည်။ ၂ မိနစ် Overlap သည် Device Clock အနည်းငယ်ကွာခြားခြင်းနှင့် တစ်ချိန်တည်းရေးသားမှုများကြောင့် Record လွတ်သွားနိုင်ခြေကို လျှော့ပေးသည်။

## 2. v2.9.4 Device များအတွက် Migration

- v2.9.4 မှာ ရှိပြီးသား Local Sync Manifest `savedAt` ကို ပထမဆုံး Cursor အဖြစ် အသုံးပြုသည်။
- ထို့ကြောင့် Baseline ရှိပြီးသား Device များသည် History အားလုံးကို Full Scan ပြန်မလုပ်ဘဲ နောက်ဆုံး Sync အချိန်နောက်ပိုင်း ပြောင်းလဲမှုများကိုသာ ဖတ်နိုင်သည်။
- Branch အသစ်ကို Device က ပထမဆုံးတွေ့သည့်အခါ ထို Branch ၏ History Collection များကို တစ်ကြိမ် Full Snapshot ဖတ်ပြီး Baseline တည်ဆောက်သည်။
- Shared Customer/Supplier Rules ယခင်က ခွင့်မပြုခဲ့လျှင် အရင် Shared Data မလွတ်စေရန် Rules ပြန်ခွင့်ပြုပြီး ပထမဆုံးအကြိမ်မှာ Full Read တစ်ကြိမ်လုပ်သည်။
- Device အသစ်တစ်ခုမှာ Manifest မရှိလျှင် Cloud Data အားလုံးကို ရယူရန် Full Initial Snapshot မဖြစ်မနေ လိုအပ်သည်။ သို့သော် ယခင်ကလို Full `getDocs` Scan ပြီးနောက် တူညီတဲ့ Listener Snapshot ကို ထပ်မဖတ်တော့ပါ။ Listener ရရှိပြီးသား Server Snapshot ကို Safe Bootstrap အတွက် အသုံးပြုသည်။

## 3. Reconnect / Background ပြန်ဝင်ခြင်း

- Browser `offline` ဖြစ်လျှင် Historical Delta Listener များကို ဖြုတ်ထားသည်။
- `online` ပြန်ဖြစ်သောအခါ နောက်ဆုံးသိမ်းထားသော Cursor ကနေ Listener အသစ်ပြန်ချိတ်သည်။
- ပုံမှန် Tab ပြောင်းတိုင်း Listener များကို မဖြုတ်/မပြန်ချိတ်တော့ပါ။ Background ထဲ 25 မိနစ်နှင့်အထက် ရှိခဲ့မှသာ Delta Listener များကို နောက်ဆုံး Cursor ကနေ ပြန်တည်ဆောက်သည်။
- Product / Category / Stock Listener များကို Realtime ဆက်ထားသည်။

## 4. Manual Sync

Cloud Sync Panel ရဲ့ ယခင် Full Scan လုပ်ဆောင်ချက်များကို ပုံမှန်အသုံးပြုမှုမှ ဖယ်ရှားထားသည်။ `Sync Now (ပြောင်းလဲမှုများသာ)` သည် လက်ရှိ Realtime / Delta Listener များမှ ရရှိပြီးသား Cloud Data နဲ့ Local Business Data ကိုသာ Reconcile လုပ်သည်။ ပုံမှန်အခြေအနေတွင် `getDocsFromServer()` Full Collection Scan မလုပ်တော့ပါ။

တူညီတဲ့ Record ကို Device နှစ်ခုက ပြိုင်တူ ပြင်ထားလျှင် အလိုအလျောက် အစားမထိုးဘဲ Conflict အဖြစ် ရပ်ထားသည်။

## 5. Listener Reuse နှင့် Branch Lifecycle

- Branch အသစ်ထည့်လျှင် Branch အသစ်ရဲ့ Listener များကိုသာ ဖွင့်သည်။
- Branch တစ်ခု ပြောင်းလဲ/ဖယ်ရှားလျှင် အခြား Branch Listener များကို အကုန်မဖြုတ်တော့ပါ။
- Listener များကို `Map` ဖြင့် Branch/Collection အလိုက် သိမ်းထားပြီး Remove/Unmount မှာ Unsubscribe လုပ်သည်။
- `OwnerAutoSyncProvider` နှင့် `AccessBootstrap` ကို React `StrictMode` အပြင်ဘက်ထားပြီး App UI ကိုသာ StrictMode အောက်မှာထားသည်။ Vite Development StrictMode effect replay ကြောင့် Firebase listener effect မလိုအပ်ဘဲ ထပ် mount ဖြစ်နိုင်ခြေကို ကာကွယ်သည်။
- Branch အသစ်/ဖျက်ခြင်းတွင် သက်ဆိုင်ရာ Branch Listener များကိုသာ ဖွင့်/ပိတ်သည်။ Branch မပြောင်းသော Listener များကို မပြန်ဖွင့်ပါ။
- Branch 1 ခုအတွက် active subscriptions 19 ခု ရှိနေဆဲ (15 branch collections + branch list + meta + 2 shared) ဖြစ်သည်။ v2.9.5 သည် subscriptions ကို 1 ခုအထိ လျှော့ချထားခြင်း မဟုတ်ပါ။ History collections မှ ပြန်ဖတ်မည့် Document များကို Cursor Query ဖြင့် လျှော့ချသည်။
- Zustand Store update အားလုံးကို မကြည့်တော့ဘဲ Sync ထဲပါဝင်တဲ့ Business Data reference ပြောင်းလဲမှသာ Reconcile schedule လုပ်သည်။ Cart typing၊ Tab ပြောင်းခြင်း၊ Active Branch UI state တို့ကြောင့် အပို Reconcile မဖြစ်စေရန် ဖြစ်သည်။

## 6. Writes နှင့် Data Safety

- Local/Cloud payload hash တူနေပါက Write မလုပ်ပါ။
- Push လုပ်မည့် Record များကို Transaction ဖြင့် Server Value စစ်ပြီးမှ Write လုပ်သည်။ ဒီ Transaction Read ကို ဖယ်မထားပါ။ Concurrent Device Update ကို မတော်တဆ overwrite မဖြစ်စေရန် လိုအပ်သော Read ဖြစ်သည်။
- Local Sync Baseline ကို Cloud Pull/Push တည်ငြိမ်ပြီးမှ Save လုပ်သည်။
- Cashier Cloud Sales / Server-side Stock Transaction ကို ဒီ Version မှာ မဖွင့်သေးပါ။ Owner Auto Sync သာ ပါဝင်သည်။

## 7. Diagnostics

Browser Developer Console မှာ အောက်ပါ count-only logs များကို ကြည့်နိုင်သည်။

- `[Minimart Sync Snapshot]` — Branch / Collection / incremental သို့မဟုတ် initial-full / ပြောင်းလဲထားသော Document အရေအတွက်
- `[Minimart Sync Reconcile]` — Local Record အရေအတွက် / လက်ရှိ tracked Cloud changes / Write candidate / Pull အခြေအနေ
- `[Minimart Sync Write]` — Candidate Record အရေအတွက်၊ Transaction chunk၊ Attempt တစ်ကြိမ်စာ ဖတ်သည့် Record အရေအတွက်ခန့်မှန်းချက်၊ အောင်မြင်သော Write အရေအတွက်

ဤ Diagnostic များကို Firebase ထဲသို့ ထပ်မံမရေးပါ။ Record အမည်၊ Customer အချက်အလက်၊ ဈေးနှုန်းတို့ကို Log ထဲ မထည့်ထားပါ။ Transaction retry ဖြစ်ပါက အမှန်တကယ် Read အရေအတွက်သည် Console ခန့်မှန်းချက်ထက် မြင့်နိုင်သည်။

## 9. Update လုပ်ရန် အရေးကြီးချက်များ

1. Laptop နဲ့ Phone နှစ်ခုလုံးမှာ JSON Backup ထုတ်ပါ။
2. `npm install` ပြီးမှ `npm run typecheck` နဲ့ `npm run build` လုပ်ပါ။
3. Build အောင်မြင်မှ GitHub Pages သို့ Deploy လုပ်ပါ။
4. Device နှစ်ခုလုံးမှာ v2.9.5 ကို တူညီစွာ Update လုပ်ပါ။
5. အရင် Firebase Config `store-mini` ကို မပြောင်းပါနှင့်။ Project အသစ်ပြောင်းရန် သီးခြား migration plan လုပ်ပြီးမှ Config ပြောင်းပါ။
6. App ကို စမ်းသပ်ချိန်မှာ localhost Port မတူတဲ့ Version နှစ်ခု (ဥပမာ 5173 နှင့် 5174) နဲ့ GitHub Production ကို တစ်ပြိုင်နက် မဖွင့်ပါနှင့်။ Origin တစ်ခုချင်းစီက Firebase Project တစ်ခုတည်းသို့ ကိုယ်ပိုင် Listener Set ဖွင့်နိုင်သည်။
7. v2.9.5 ပထမဆုံးအသုံးပြုမှုမှာ Manifest မရှိသော Device အသစ်အတွက် Full Bootstrap တစ်ကြိမ်လိုအပ်သည်။ Baseline ရှိပြီးသား Device များမှာ Manifest `savedAt` Cursor အခြေခံ Incremental Query ကို သုံးသည်။
8. Firestore Usage Limit ကျော်နေသည့် Project တွင် Quota ပြန်မရသေးခင် First Bootstrap သို့မဟုတ် စမ်းသပ်မှုများ ထပ်မလုပ်ပါနှင့်။
