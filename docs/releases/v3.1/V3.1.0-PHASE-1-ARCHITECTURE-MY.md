# Minimart POS v3.1.0 — Phase 1 Architecture Foundation

**Base source:** v3.0.2 — Branch Shipment Batch Validation Fix  
**Phase status:** Architecture / type-contract preparation only  
**Production behavior:** No new Cashier page, payment flow, notification, Firestore collection, or rule is activated in this phase.

## 1. Phase 1 ရဲ့ ရည်ရွယ်ချက်

v3.0.2 မှာ အလုပ်လုပ်နေတဲ့ Login, POS, Sales, Stock, Stock Transfer, Branch Shipment/Receiving, Owner Approval, Offline Queue နဲ့ Cloud Sync တို့ကို မပြောင်းဘဲ v3.1.0 အတွက် Data Contract နဲ့ Permission Design ကို ကြိုတင်သတ်မှတ်ရန်။

ဒီ Phase မှာ TypeScript compile-time type တွေကိုသာ ထပ်ထည့်ထားပါတယ်။ Firebase ကို data write/read အသစ် မလုပ်ပါ။ Firestore Rules ကိုလည်း မပြောင်းထားပါ။

## 3. v3.1.0 အတွက် အကြံပြု Data Structure

### 3.1 Cashier Expense — ရှိပြီးသား Collection ကို တိုးချဲ့ရန်

**အသစ် Collection တစ်ခုထပ်မဖန်တီးဘဲ** ရှိပြီးသား path ကို ဆက်သုံးရန် အကြံပြုသည်။

`businesses/{businessId}/branches/{branchId}/expenses/{expenseId}`

လက်ရှိ fields များကို မဖျက်ဘဲ optional metadata ကိုသာ ထပ်တိုးမည်။

- `createdByUid`, `createdByEmail`, `createdByName`
- `fundedBy`: `cashier-personal` / `branch-cash` / `branch-kpay`
- `paymentMethod`: `cash` / `kpay`
- `approvalStatus`: `not-required` / `pending` / `approved` / `rejected`
- `approvedAt`, `approvedByUid`, `approvedByName`
- `rejectedAt`, `rejectedByUid`, `rejectionReason`
- `receiptImageRef`, `updatedAt`, `updatedByUid`

Legacy Expense record များတွင် ဒီ fields မရှိနိုင်သောကြောင့် optional အဖြစ်သာ ထားရမည်။ Migration လုပ်စဉ် historical records အားလုံးကို အတု UID/approval status ဖြည့်ခြင်း မလုပ်ရ။

### 3.2 Cashier Settlement — သီးခြား Ledger

Owner က Cashier တစ်ယောက်ချင်းစီထံ Cash သို့မဟုတ် KPay ဖြင့် ပေးချေသည့် ငွေကို Expense အဖြစ် ထပ်မတွက်ဘဲ သီးခြား Settlement record ထားရန်။

အကြံပြု path:

`businesses/{businessId}/branches/{branchId}/cashierSettlements/{settlementId}`

အဓိက fields:

- `cashierUid`, `cashierName`, `branchId`
- `purpose` (လုပ်ငန်းသုံး အမျိုးအစားကို Owner နဲ့ အတည်ပြုပြီးမှ controlled values သတ်မှတ်မည်)
- `amount`, `paymentMethod` (`cash` / `kpay`), `status`
- `receiverAccountName`, `receiverAccountNumber`, `transactionReference`
- `receiptImageRef`, `note`
- `createdAt`, `createdByUid`, `paidAt`, `paidByUid`

**မူလစာရင်းမှန်ကန်ရေး:** Expense တစ်ခုကို Cashier ကိုယ်ပိုင်ငွေနဲ့ အရင်စိုက်သုံးထားလျှင် Expense ကို တစ်ကြိမ်သာ အသိအမှတ်ပြုမည်။ Owner က KPay နဲ့ ပြန်အမ်းပေးသည့် Settlement ကို Expense ဒုတိယတစ်ကြိမ်အဖြစ် မတွက်ရ။

### 3.3 Branch KPay Account

Branch တစ်ခုချင်းစီရဲ့ ဆိုင်ပိုင် KPay လက်ခံအကောင့်ကို Cashier သို့ ပေးချေမည့် Cashier ရဲ့ ကိုယ်ပိုင် KPay account နဲ့ မရောထွေးစေရ။

အကြံပြု path:

`businesses/{businessId}/branches/{branchId}/paymentAccounts/{accountId}`

- `provider: kpay`
- `accountName`, `accountNumber`, `label`, `isActive`
- `createdAt`, `updatedAt`, `updatedByUid`

Cashier ထံငွေပေးရန် အသုံးပြုမည့် receiver account details ကို Settlement record ထဲမှာ အချိန်အလိုက် snapshot ထားနိုင်သည်။

### 3.4 Cashier Expense Policy

Owner က Cashier တစ်ယောက်ချင်းစီအလိုက် Limit သတ်မှတ်နိုင်ရန် policy model ကို ကြိုတင်သတ်မှတ်ထားသည်။ ဒါပေမဲ့ Limit က **တစ်ကြိမ်အသုံးစရိတ်အလိုက်လား၊ နေ့စဉ်/အပတ်စဉ်/လစဉ်လား၊ Cashier ကို ကြိုတင်အပ်ထားတဲ့ငွေလက်ကျန်လား** ဆိုတာကို လုပ်ငန်းပုံစံအရ အတည်ပြုပြီးမှ runtime validation ထည့်မည်။

### 3.5 Shipment Notification

လက်ရှိ `stockShipments` record ကို ကုန်ပို့/လက်ခံ/Approve အခြေအနေအတွက် source of truth အဖြစ် ဆက်သုံးရန်။ In-app notification အတွက် အစပိုင်းတွင် Firestore notification collection အသစ်မဖန်တီးဘဲ ရှိပြီးသား Shipment listener မှ event ကို အသုံးပြုနိုင်သည်။

App ပိတ်ထားချိန် Push Notification အတွက် FCM လိုအပ်သည်။ FCM send လုပ်ခြင်းကို Client မှ secret key မပါဘဲ ယုံကြည်စိတ်ချရသော server-side trigger (ဥပမာ Cloud Functions) မှသာ လုပ်ဆောင်ရမည်။ v3.0.2 ZIP ထဲတွင် Cloud Functions backend မပါသေးသဖြင့် ဒီအပိုင်းသည် နောက် Phase အလုပ်ဖြစ်သည်။

## 4. Permission Matrix — ရည်ရွယ်ထားသော စည်းမျဉ်း

| Resource / Action | Owner | Cashier |
|---|---|---|
| မိမိ Branch Expense ဖတ်ရန် | All branches | ကိုယ်တိုင်ဖန်တီးထားသော record သာ |
| Expense အသစ်တင်ရန် | ရ | မိမိ UID ဖြင့်သာ |
| Expense Approval / Rejection | ရ | မရ |
| Expense record အဟောင်း ပြင်/ဖျက် | ရ (audit အပါအဝင်) | Submit ပြီးလျှင် မရ |
| Cashier Settlement ဖန်တီး/ပေးချေ | ရ | မရ |
| ကိုယ်ပိုင် Settlement History ဖတ် | ရ | ကိုယ့် UID record သာ |
| Branch KPay Account ပြင် | ရ | မရ |
| Branch KPay Account ဖတ် | ရ | POS လိုအပ်ချက်ကို အတည်ပြုပြီးမှ ဆုံးဖြတ်မည် |
| Shipment Dispatch / Approve | ရှိပြီးသား Owner flow | မရ |
| Assigned Shipment လက်ခံအတည်ပြု | ရ | `canReceiveStock` ရှိသူသာ |

Firestore Security Rules က UI permission ကိုသာ မယုံကြည်ဘဲ `request.auth.uid`, member role/status, assigned `branchIds`, payload owner UID နဲ့ allowed field changes ကို server-side စစ်ဆေးရမည်။

## 5. Firebase Read / Write Optimization Design

1. လက်ရှိ v2.9.5 incremental sync/cursor, v2.9.6 local diagnostics ကို မဖျက်ရ။
2. Cashier Expense နဲ့ Settlement အသစ်များကို Cashier UID filter ပါသော query ဖြင့်သာ ဖတ်ရန်။ Branch collection အားလုံးကို Cashier ထံ full download မလုပ်ရ။
3. Owner သည် လိုအပ်သော branch များ၏ Finance History ကိုသာ ဖွင့်သည့်အခါ fetch လုပ်နိုင်ရန် စီစဉ်ရန်။
4. Shipment Notification အတွက် တူညီသော Shipment document ကိုဖတ်ပြီး Notification document များ ထပ်ရေးခြင်းကို ပထမအဆင့်တွင် ရှောင်ရန်။
5. FCM push ပို့ခြင်းကို shipment event တစ်ခုချင်းအတွက် server-side trigger မှ တစ်ကြိမ်တည်းပို့ရန်။ Token refresh / duplicate event ကို ကာကွယ်ရန်။
6. Finance write များတွင် stable document ID / idempotency key သုံးပြီး retry ကြောင့် duplicate settlement မဖြစ်စေရန်။
7. Read/Write/Listener Diagnostics သည် client-side estimate ဖြစ်ပြီး Firebase Console Usage ကိုသာ billable usage အတည်ပြုချက်အဖြစ် ယူရန်။
8. Owner Auto Sync ၏ လက်ရှိ branch listeners အရေအတွက်ကို မတိုးခင် data access လိုအပ်ချက်၊ page visibility နဲ့ listener lifecycle ကို စမ်းသပ်ရန်။

## 6. Phase 1 မှာ မပြောင်းထားသောအရာများ

- Firebase Project Config / Auth / Owner UID / Business ID
- `firestore.rules`
- Owner / Cashier Login flow
- POS Checkout / Sales / Stock / Barcode
- Stock Transfer / Branch Shipment / Receiver Approval
- LocalStorage state migration / schema version

`src/types/finance.ts` သည် compile-time contract file သာဖြစ်ပြီး Firestore data အသစ်ကို မဖန်တီးပါ။ Existing `Expense` type တွင် optional fields တိုးထားခြင်းက legacy record တွေနဲ့ backward-compatible ဖြစ်စေရန်သာ ဖြစ်သည်။

## 7. Phase 2 မစတင်မီ အတည်ပြုရန် လိုအပ်သောအချက်များ

1. Cashier တစ်ယောက်ချင်းစီအတွက် “ကိုယ်ပိုင်အသုံးစရိတ်” သည် အသုံးစရိတ် Limit လား၊ Owner က ကြိုတင်အပ်ထားသော အသုံးစရိတ်ငွေလက်ကျန်လား၊ နှစ်မျိုးလုံးလား။
2. Limit သတ်မှတ်ပုံသည် transaction တစ်ခုချင်း၊ နေ့စဉ်၊ အပတ်စဉ်၊ လစဉ် မည်သည့်ပုံစံလဲ။
3. Owner က KPay နဲ့ Cashier ကို ရှင်းပေးခြင်းသည် Expense ပြန်အမ်းခြင်း၊ Advance၊ Salary၊ အခြား ဘယ်ရည်ရွယ်ချက်တွေ ပါသလဲ။
4. Cashier ရဲ့ KPay လက်ခံအကောင့်ကို Owner က တစ်ကြိမ်သိမ်းထားပြီး နောက်ပိုင်း Settlement တွေမှာ ပြန်သုံးမလား။
5. Branch ရဲ့ KPay အကောင့်အချက်အလက်ကို Cashier POS မှာ မြင်ရဖို့ လို/မလို။

ဒီအချက်တွေ မအတည်ပြုမချင်း limit enforcement, payment UX, Firestore Rules အသစ်တွေကို production အတွက် မဖွင့်ရ။
