# Minimart POS v3.2.6 — Barcode & Android Receipt Printing

**Release scope:** Android-first fast checkout with Bluetooth/USB HID barcode scanners and ZYWELL ZM04 80 mm thermal receipt printing.

## Goals

1. Keep the existing React/Vite web app and GitHub Pages deployment working.
2. Support Bluetooth and USB scanners that expose themselves as Android HID keyboards. Do not require pairing APIs for HID scanners; Android handles their keyboard input.
3. Keep the current product barcode/SKU scan-to-cart behavior and add continuous-scan readiness without stealing focus from payment, dialogs, or text fields.
4. Add safe support for individually purchased sticker barcodes. A registered unit barcode must resolve to exactly one in-stock physical unit; a sold/returned/damaged/missing unit must not be sold as in-stock. The sale and unit-status transition must be persisted atomically in the cloud path before the receipt is treated as final.
5. Add Android native printing for ZYWELL ZM04 using the manufacturer's Android SDK or a verified ESC/POS transport. Keep browser/system printing as a fallback for desktop and web.
6. Make receipt printing retryable without creating a second sale or reducing stock again.

## POS user flow

`Scan products → review cart and total → choose Cash/KPay/Credit → confirm payment → persist one sale → print the same voucher → clear cart and return scanner to ready state`.

A scan must never automatically complete a sale. The cashier must review the basket and confirm payment. Cash must include amount received and change; KPay must retain branch account and transaction-reference validation; Credit must retain customer validation.

## Scanner behavior

- Bluetooth and USB HID scanners use the same keyboard-input pipeline.
- Support scanners configured with Enter as suffix; ignore a scan until the full code is received.
- Maintain focus only while POS scan-ready mode is enabled and no modal/form field is active.
- Preserve manual product search and camera scanning.
- Prevent a duplicate rapid scan event from adding the same single physical-unit barcode twice.
- Unknown, duplicate, disabled, or already-sold unit barcode must show a clear warning and must not change cart or stock.
- Product-level barcode repeats increment quantity; unit-level sticker barcode maps to one physical unit only.

## Printer behavior

- Target Android phone + ZYWELL ZM04, 80 mm receipt roll, with 72 mm printable area where the installed printer variant supports that specification.
- Implement printer discovery/connect/status/test-print/print/disconnect in a native Android bridge.
- Prefer manufacturer's official Android SDK after confirming the exact ZM04 interface variant and SDK sample. Otherwise use a verified ESC/POS transport for the confirmed Bluetooth/USB profile.
- Render Burmese Unicode receipt text to a bitmap/raster image if the device's built-in fonts cannot render Myanmar correctly.
- Include shop/branch name, voucher number, date/time, item name, quantity/unit, unit price, line total, subtotal, discount, grand total, payment method, cash received/change or KPay reference, due amount, and footer.
- Keep 58/80 mm browser print preference and desktop `window.print()` fallback.
- Printing failure must not roll back a saved sale. Store print status against the saved voucher and allow retrying that same voucher.

## Critical data-safety rules

- Sale creation and stock deduction happen once only.
- A print retry must use the existing sale ID and voucher number; it must never call checkout again.
- Unit barcode status changes and the sale record must be consistent. Do not implement unit barcode scan-to-sale as UI-only local state.
- Preserve Firebase Authentication, Owner/Cashier authorization, business/branch IDs, current price snapshots, existing offline queue, backup/restore, and current GitHub Pages workflow.
- Do not deploy Firestore Rules or Cloud Functions to Production as part of the web/Android UI release without separate QA and approval.

## Android packaging

- Use a Capacitor Android shell around the existing Vite app; do not rewrite the POS.
- Keep Android-only native printer code under the Android/native bridge and keep browser fallbacks in the web app.
- Commit source/configuration and lockfiles. Ignore `node_modules`, `dist`, Android `.gradle`, Android `build`, `local.properties`, signing keys, and generated APK/AAB output unless release artifacts are deliberately attached.

## Release gates

- Web `npm run qa` passes.
- Android debug APK builds.
- Bluetooth HID scanner and USB HID scanner each pass continuous-scan testing.
- Product barcode and unique unit sticker behavior pass without duplicate sale/stock changes.
- ZM04 connection and 80 mm Burmese Unicode receipt pass on the actual device.
- Printer-off / paper-out / disconnect / retry do not duplicate the sale.
- Owner and Cashier login, role permissions, sales, batch stock, offline sync, and desktop browser print regression pass.
