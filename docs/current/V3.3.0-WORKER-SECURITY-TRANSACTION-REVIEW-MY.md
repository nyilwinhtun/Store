## 2. Cashier Void / Return (new)

- Authorization: active Cashier member for exactly the assigned branch; business
  active; branch payload `status === 'active'`.
- Request validity: `branchId`, `saleId`, `requestId`, `deviceId`, reason length,
  strict allowlists; unknown fields rejected.
- Void restores Product stock, Batch quantity, and only Units whose stored
  `status === 'sold'` and `saleId` matches. Audit record is written in the same
  commit.
- Return verifies each Unit against the original Sale and prevents over-return
  using `returnedProductQuantities` / `returnedBatchQuantities`. Only `restock`
  Units increase stock; `damaged` Units become `status: 'damaged'` with reason.
- Credit Return reduces `dueAmount`; any remaining value is marked
  `credit-refund-review`. KPay Return is marked `kpay-pending`. Cash Return is
  marked `cash-refunded`; no cash drawer movement is implied by the API.
- Idempotency: Void replay keyed by `auditEvents/{saleId}__void.voidRequestId`;
  Return replay keyed by `saleReturns/{requestId}.fingerprint`; both return the
  original response payload without a second stock write.
- Double restocking is prevented by Unit status checks, prior returned quantities,
  and transaction isolation.
- A Sale with any Return cannot be Voided. A Voided Sale cannot be Returned.
- Worker endpoints authorize Cashiers. Owner adjustments use the trusted
  `cashierSaleVoid` / `cashierSaleReturn` Cloud Functions (business `ownerUid`),
  not the Worker POC.

## 3. Residual Risks

1. JWKS, revocation, and real Firestore REST transactions have not run against a
   real Spark Staging project. Emulator evidence is not Staging evidence.
2. The service account bypasses Firestore Rules. The Worker code is therefore the
   security boundary; every Rules invariant must stay implemented in the Worker.
3. A fully offline browser cannot prove elapsed time. The Worker holds expired
   offline commits (`expired-hold`) and keeps stock reserved; it does not claim
   clock-independent enforcement on the device.
4. Scheduled expiry processes one allowance/lease per transaction. At large
   volume this must be segmented to stay inside Workers Free subrequest limits.
5. Cash refund status is accounting metadata. It does not open a cash drawer or
   create a cash movement record.

## 4. Service-Account Credential Rotation

Do this only in the Owner's terminal and only for the intended project.
Never paste the JSON into chat, Git, screenshots, source, or logs.

1. Create a new key for the Staging service account in Google Cloud/Firebase
   Console (`Project settings → Service accounts → Generate new private key`).
2. In the Worker directory, replace the secret from a local file:
   `npx wrangler secret put FIRESTORE_SERVICE_ACCOUNT < "$HOME/Downloads/minimart-staging-service-account.json"`
3. Deploy the Worker with an explicit Owner-authorized command, then re-run the
   Staging smoke matrix (auth, allowlist denial, allowance/lease boundaries,
   Void/Return idempotency).
4. After verification, disable/delete the previous key in Google Cloud IAM.
5. Remove the downloaded file with `rm -P` and confirm no copy remains in
   Downloads/Trash backups.
6. Record the rotation date and operator in the Owner's private operations log.
   Do not record the key itself.

## 5. Incident Response (Suspected Key Exposure)

1. **Contain** — disable/delete the exposed service-account key immediately.
2. **Rotate** — create a new key, update the Cloudflare secret, redeploy the Worker.
3. **Revoke sessions** — disable the affected Firebase Auth Cashier/Owner account
   if credential misuse is suspected; Firebase `validSince` revocation then makes
   old ID tokens fail.
4. **Preserve evidence** — do not delete Sales, Returns, pending queue entries,
   audit records, or Worker logs. Export read-only copies where available.
5. **Assess** — review `auditEvents`, `saleReturns`, reservation ledgers, and
   unusual stock changes; compare local pending queues against cloud Sales.
6. **Recover** — release reservations only through Owner reconciliation after
   review. Never auto-delete pending Sales or expired holds.
7. **Notify** — inform the Owner with scope, time window, and actions taken.
   Never include the key or full token in the report.
8. **Prevent recurrence** — prefer short-lived keys/workload identity if the plan
   supports it; restrict IAM to `roles/datastore.user` and
   `roles/firebaseauth.viewer`; keep Worker secrets out of build artifacts.
