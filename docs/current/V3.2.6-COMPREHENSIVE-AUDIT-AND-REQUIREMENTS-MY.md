## 2. Executive summary

### 2.1 What is healthy

- **Offline-first architecture is sound.** Zustand state persists to IndexedDB; cashier
  sales/expenses/cash use durable IndexedDB outboxes with Web Locks and idempotent
  Firestore transactions. This must not be weakened.
- **Financial integrity is protected.** Sale totals, discounts, paid/due reconciliation,
  stock deltas, batch deltas, and KPay references are validated server-side by Rules and
  by atomic transactions. Keep this.
- **Multi-branch isolation works.** Cashiers are assigned to one active branch by Rules;
  Owner-only pages and writes are enforced in Rules, not just hidden in navigation.
- **No image bandwidth cost.** Shop logos/banners are IndexedDB blobs referenced by
  `local-image:` and are stripped from cloud payloads. Firestore/Storage image cost is
  effectively zero.
- **The existing palette is already Emerald-based**, so the recommended design direction
  is an evolution, not a rewrite.

### 2.2 Highest-risk findings

| # | Finding | Severity | Why it matters |
|---|---|---|---|
| R1 | `activityLogs` is a **full realtime listener per branch**, grows without bound in the cloud, and is imported back into local state without the 300-entry cap. | **P0** | Dominates Owner cold-start reads (hundreds of thousands in mature shops), grows IndexedDB, and can exceed the 50k/day Spark read quota in one sync. No financial calculation depends on it. |
| R2 | The sync manifest is stored in **LocalStorage** and fully `JSON.parse`d once per listener and fully stringified per reconcile. | **P0** | LocalStorage ~5 MB ceiling is reached around ~20k records. Failure halts sync (`saveManifest` returns false). Parsing 21×N times per login causes main-thread stalls. |
| R3 | KPay sales store **only the transaction reference**, not the receiving account name/number at the time of sale. | **P0 (business/legal)** | Owner account edits overwrite the only account context; historical transactions cannot prove where money was received. Violates the stated requirement. |
| R4 | Cashier listens to **full** `cashShifts`, `cashMovements`, `customerPayments` collections. | **P1** | Continuous growth in read cost and initial-snapshot latency in long-running branches. |
| R5 | Owner sync attaches listeners to **archived branches** as well as active ones. | **P2** | Wasted listeners/reads, especially after branch consolidation. Archived data must remain restorable. |
| R6 | `includeMetadataChanges: true` on every listener. | **P2** | Extra callback churn/main-thread work; no read-cost benefit. |
| R7 | Owner Dashboard/Branch Overview recompute nested per-branch filters on render; POS renders every product tile. | **P2** | UI jank at 1,000+ products / 8+ branches, independent of Firebase. |
| R8 | Login lacks a real loading indicator, `aria-busy`, error placement near the fields, and mobile height control. | **P2 (UX)** | Looks unfinished on slow networks; feedback appears below the fold on phones. |
| R9 | 110 CSS declarations use 8–10px type; many controls are 25–31px. | **P2 (accessibility)** | Myanmar glyphs become hard to read; touch targets fall below 44px. |
| R10 | 644 hard-coded hex literals / 397 distinct values / 227 dark-mode override selectors. | **P3** | Theme changes are brittle; some light-only colors leak into dark mode. |

### 2.3 Decisions requested from the Owner

1. **Approve R1/R2/R3 as the P0 implementation scope.** These are integrity/scalability
   repairs, not redesigns.
2. **Choose the color direction** (recommendation: Vibrant Emerald evolution, Section 6).
3. **Confirm `activityLogs` retention policy** (recommendation: keep all cloud history,
   but stop realtime full sync; load by date window on demand and export/archive).
4. **Confirm whether KPay account snapshots should be added to customer payments and
   cashier settlements**, not only POS sales (recommendation: yes, same pattern).

## 4. (B) Firebase cost optimization report

### 4.1 What is actually billed

- Every server document returned by a listener/query counts as a read. Cached local-cache
  snapshots do not.
- Listener **initial snapshots** count for each returned document; subsequent changed
  documents count per change. Reconnect after network loss may re-read.
- Each `transaction.get` and each `getDocFromServer` counts. Rules `get()/exists()` reads
  are also billed (same-document lookups are cached per request).
- Every `set/update/delete` counts as a write/delete, including transaction writes.
- Cloud Functions invocations are billed separately under Blaze; blocking Auth functions
  also require Identity Platform.
- Firebase Storage is not used for shop images, so there is no image egress/storage cost.

### 4.2 Measured architecture facts (from code)

**Owner login / sync fan-out**

- 21 branch record kinds × N branches (`branchRecordKinds`), plus:
  - branches list listener,
  - meta listener,
  - 2 shared listeners (customers, suppliers).
- 16 kinds are incremental after a cursor; **5 are full collections**:
  `categories`, `products`, `heldItems`, `stockUnitRegistries`, `activityLogs`
  (`OwnerAutoSync.tsx:35-38`).
  The inline comment says only categories/products stay full; the code includes three more.
- `activityLogs`, `stockUnitRegistries`, and `heldItems` therefore grow with usage.
- Branches listener does not filter archived branches (`OwnerAutoSync.tsx:462-466`).
- `includeMetadataChanges: true` on all listeners (`OwnerAutoSync.tsx:30`).
- Incremental query uses `updatedAt >= cursor − 120s`; cursors are stored per
  branch/kind in LocalStorage (`OwnerAutoSync.tsx:419-450`).
- Manifest is read (`JSON.parse`) per listener attach and per shared attach
  (`readManifest` at `CloudSyncPanel.tsx:152`, called at `OwnerAutoSync.tsx:424, 511, 171, 332`).
- Manifest is fully stringified on every successful reconcile
  (`saveManifest` at `CloudSyncPanel.tsx:168`).
- Reconcile runs 700 ms after a local change and 250 ms after a remote change
  (`OwnerAutoSync.tsx:311`), hashing every local record (`buildLocalItems`).

**Per cashier sale (durable transaction)**

At `src/lib/cashierSalesSync.ts`:

- Reads: `2 + P + B (+1)` where P = changed products, B = changed batches, +1 for a credit
  customer.
- Writes: `2 + P + B (+1)` (sale + audit event + product/batch updates + customer).
- Plus listener delivery of the changed product/batch/sale documents.
- This cost is **necessary for stock/financial integrity** and should not be reduced.

**Cashier cold start**

- 1 branch doc
- 6 full branch collections: categories, products, stockBatches, cashShifts,
  cashMovements, customerPayments (`CashierAutoSync.tsx:259-264`)
- 1 shared customers listener
- optional stockShipments
- 3 own-record queries with `where(uid)`, `orderBy`, `limit(100)` = up to 300 docs
  (`CashierAutoSync.tsx:310-370`)
- No cursors for cash shifts/movements/payments: they grow forever.

**Auth / access**

- `beforeUserSignedIn` performs 3 Admin SDK reads per login (business, member, branch)
  (`functions/src/index.ts:45-87`).
- `AccessBootstrap` does `getDocFromServer` (1 read) with cached fallback, then 1 member
  read for cashiers (`AccessBootstrap.tsx:41-50`).
- `CashierSettlementManagementPage` lists members once for owner name mapping.

**Images / analytics**

- Shop images are IndexedDB blobs; no Firestore/Storage bandwidth.
- Dashboard, analytics, sales history, and reports are computed from local state; no
  Firestore aggregate queries.
- `salesAudit.ts` uses a bounded `limit(100)` server query on demand.
- Three composite indexes exist; no excessive index set.

### 4.3 Cost formulas

**Owner cold start (first sync on a device / after reset / no cursor):**

```
reads ≈ 4 + N + 1 + (C + S + G)
      + N × (K + P + U + H + A + I)
```

- `4` = business, member/owner check, meta, branch list overhead (approx.)
- `N` = branches listened to (currently including archived)
- `C/S/G` = shared customers, suppliers, price groups
- `K/P/U/H/A` = categories, products, stock unit registries, held items, activity logs
- `I` = incremental records returned since cursor (sales, batches, cash, etc.)

**Owner steady-state login (cursor present):**

```
reads ≈ 4 + N + 1 + (C + S + G) + N × (K + P + U + H + I_recent)
```

`I_recent` is small because of the `updatedAt` cursor.

**Cashier cold start:**

```
reads ≈ 5 + 1 + (K + P + B + SH + MV + CP + C) + 300 + shipments
```

- `5` = auth/access checks (approx.)
- `SH/MV/CP` = all cash shifts, cash movements, customer payments in the branch

**Per cashier sale:**

```
reads  = 2 + P + B (+1 credit)
writes = 2 + P + B (+1 credit)
```

**Per owner sale:** 1 sale write; changed product docs also sync (1 read + 1 write each),
plus manifest/reconcile CPU.

   Spark **50,000 reads/day** free cap. On Blaze it becomes a latency/cost spike, not a
   hard failure.
2. **Growth:** activity logs, stock units, and cash collections grow without bound, so the
   spike worsens every month.
3. **Blocking Auth functions already require Blaze + Identity Platform**, so Spark is not
   a viable deployment target for this app regardless of Firestore volume. Do not change
   the billing plan as part of this work.
4. **Budget alerts do not stop spending.** They only notify. Spending caps are not a
   Firestore feature.

### 4.5 Cost hotspots (ranked)

| Rank | Hotspot | Impact | Verdict |
|---:|---|---|---|
| 1 | Full `activityLogs` listener per branch + unbounded cloud growth + uncapped import | Largest cold-start and change-read source; local state growth | **FIX (P0)** |
| 2 | Full `stockUnitRegistries` and `heldItems` listeners | Grows with unit stickers and held carts | **IMPROVE (P1)** |
| 3 | Full cashier `cashShifts` / `cashMovements` / `customerPayments` | Grows with branch age | **IMPROVE (P1)** |
| 4 | 21 listeners × N branches, including archived | Listener setup, snapshot reads, reconnect churn | **IMPROVE (P2)** |
| 5 | Manifest LocalStorage parse/stringify per listener/reconcile | CPU, memory, 5 MB ceiling | **FIX (P0)** |
| 6 | `includeMetadataChanges: true` | Callback churn | **IMPROVE (P2)** |
| 7 | 120 s cursor overlap | Small duplicate reads; protects clock skew | **KEEP** |
| 8 | Per-sale transaction reads/writes | Necessary for stock/financial integrity | **KEEP** |
| 9 | Blocking Auth 3 reads/login | Necessary for security | **KEEP** |
| 10 | 3 composite indexes | Necessary for bounded queries | **KEEP** |

### 4.6 Recommended optimizations

Each item states the integrity guardrail that must hold.

#### O1 — Stop full realtime sync of `activityLogs` (P0)

- **Existing:** full listener per branch; cloud unbounded; imported into local state without
  the 300 cap; hashed and merged on every reconcile.
- **Desired:** keep the audit trail, but (a) sync only the newest N days or N entries,
  (b) load older entries on demand with cursor pagination, (c) never auto-delete cloud
  history without approval, (d) keep local writes immediate.
- **Affected:** `OwnerAutoSync.tsx`, `CloudSyncPanel.tsx`, `usePosStore.ts`, audit pages.
- **Expected saving:** 60–90% of Owner cold-start reads and a large share of change reads
  in mature shops.
- **Compatibility:** audit logs are informational, not a balance input. No financial
  formula reads them. Existing documents remain; only the sync window changes.
- **Test:** new log appears immediately; older history loads on demand; no duplicates;
  reset/restore still works; audit export unchanged.

#### O2 — Move the sync manifest to IndexedDB with an in-memory cache (P0)

- **Existing:** full JSON in LocalStorage; parsed per listener, stringified per reconcile;
  failure halts sync.
- **Desired:** persist manifest in IndexedDB (new object store or a dedicated DB), keep
  only a small `{version, savedAt, recordCount}` marker in LocalStorage for fast checks,
  cache the parsed manifest in memory per session, and write debounced/chunked.
- **Affected:** `CloudSyncPanel.tsx` (`readManifest`, `saveManifest`), `syncSafety.ts`,
  startup/reset paths.
- **Expected saving:** eliminates 21×N full parses per login and the 5 MB ceiling;
  reduces login jank and storage-failure sync halts.
- **Compatibility:** must preserve atomic baseline semantics; a failed manifest write
  must still block reconcile (never push without a baseline); reset markers must still
  invalidate the baseline.
- **Test:** medium/large seeded dataset (>20k records); kill browser mid-write; verify
  no duplicate/tombstone push; conflict halt unchanged.

#### O3 — Bound cashier cash collections (P1)

- **Existing:** full `cashShifts`, `cashMovements`, `customerPayments`.
- **Desired:** window by ledger start date or trailing 90 days, with pagination for older
  history; keep opening balances so totals remain correct; never break cash reconciliation.
- **Affected:** `CashierAutoSync.tsx`, finance/ledger calculations in `usePosStore.ts`.
- **Expected saving:** 50–85% of cashier cold reads in branches older than 3 months.
- **Compatibility:** **must prove** that ledger totals use opening balance + windowed
  movements equivalently. If they require full history, introduce an aggregated opening
  snapshot first, or defer this item.
- **Test:** seeded 12-month branch; compare cash/KPay expected balances before/after;
  shift close; settlement.

#### O4 — Exclude archived branches from realtime sync (P2)

- **Existing:** branches listener returns all; listeners attach for every branch ID.
- **Desired:** realtime only for `active` branches; archived branch data fetched on demand
  when the Owner opens archive/restore, or via a lightweight explicit refresh.
- **Affected:** `OwnerAutoSync.tsx`, `App.tsx` branch views.
- **Expected saving:** proportional to archived branch count (often 30–70% listener
  reduction after consolidation).
- **Compatibility:** archived data must remain restorable and exportable; no deletes.
- **Test:** archive → restart → restore; archived sales/inventory reappear intact.

#### O5 — Disable metadata-only listener callbacks (P2)

- **Existing:** `includeMetadataChanges: true`.
- **Desired:** `false`; track pending local writes via the store/queue, not metadata
  callbacks.
- **Affected:** `OwnerAutoSync.tsx`, `CashierAutoSync.tsx`.
- **Expected saving:** less callback/render churn; no direct read reduction.
- **Compatibility:** pending-write UI must still work.
- **Test:** offline write → online; status transitions still correct.

#### O6 — Reduce listener fan-out for low-churn kinds (P2, only after measurement)

- Candidate kinds: supplier payments, purchase returns, stock transfers, finance
  reconciliations. Replace realtime with a 60–120 s pull while the tab is visible.
- **Risk:** multi-device latency. Do not do this until diagnostics show it matters.
- **Test:** two devices; edits propagate within the documented interval.

#### O7 — Keep per-sale transactions unchanged (no optimization)

- The transaction reads/writes are the price of correctness. Do not batch multiple sales
  into one transaction or skip `transaction.get`; that would break idempotency and stock
  validation.

#### O8 — Keep dashboard/analytics local (no change)

- No Firestore aggregate queries are used. Preserve this; do not move dashboard math to
  Cloud Functions or Firestore aggregation unless a measured need appears.

### 4.7 Indexes

- Keep the three composite indexes (sales, expenses, cashier settlements).
- They support the `limit(100)` ordered cashier queries and prevent full scans.
- No additional indexes are recommended until a query plan proves a need.
- A missing deployed index triggers the existing `failed-precondition` fallback; keep it.

### 4.8 Assumptions that require Firebase Console data

1. Exact document counts per collection/branch (use Console or a one-off read-only count).
2. Real daily active devices, logins per device, and sales per day.
3. Actual listener reconnect frequency and cache-hit ratio.
4. Cloud Functions invocations and Identity Platform MAU.
5. Exact Firestore region and current SKU pricing (the rate bands above are published
   list rates, not a quote for this project).
6. Whether the project is already Blaze (required by the blocking Auth functions).
7. Current daily usage graph vs the 50k/20k free caps.

### 4.9 Monitoring and budget guidance

- Review Firebase Console → Usage and billing weekly during rollout.
- Create budget alerts at 50%, 80%, and 100% of a chosen monthly budget.
- **State clearly in operations docs: alerts notify; they do not cap or stop spending.**
- Keep the local diagnostics panel (`firestoreDiagnostics`) as a per-device sanity check;
  it counts app-level operations only and excludes Rules reads and other devices.
- Optionally add Firebase App Check after approval to reduce abusive traffic; it is an
  ADD, not part of this audit.

## 8. KPay account-history compliance (F-13/F-30/F-31)

### 8.1 Requirement restated

- Owner can change each branch's Account Holder Name and KPay Number at any time.
- Existing historical transactions retain the original payment account details.
- Cashiers can never change account details.

### 8.2 Current behavior (verified)

- Owner editing works: `BranchFinanceManagementPage.tsx:198-203, 301-305` updates
  `settings.kpayAccountName/kpayAccountNumber/kpayAccountLabel`.
- Cashiers have no UI path, and Rules make `branches/{id}` create/update/delete
  **Owner-only** (`firestore.rules:730-736`). This part is correct.
- POS reads the current account for display and validation (`App.tsx:604, 1092-1093`),
  and a sale stores only `kpayTransactionReference` (`App.tsx:666-676`;
  `usePosStore.ts:108-148`).
- Therefore, changing the account today changes the only context available for past
  KPay sales. Historical receipts/exports cannot prove which account received the money.

### 8.3 Required fix (data-compatible, additive)

Add optional snapshot fields to the `Sale` type and write them at sale time:

```ts
kpayAccountNameSnapshot?: string;
kpayAccountNumberSnapshot?: string;
kpayAccountLabelSnapshot?: string;
```

Rules for implementation:

1. Write snapshots only when `paymentMethod === 'KPay'`, from the branch settings the
   cashier actually saw at sale time.
2. Keep them **optional** so every legacy sale remains valid.
3. **Do not** backfill legacy sales with current account values. Display "not recorded"
   for legacy KPay sales; inventing history is worse than a blank.
4. **Do not** make Rules require snapshot equality with current branch settings.
   A queued offline sale may commit after the Owner changes the account; equality would
   reject a legitimate sale. Validate type/length only:
   - name: string, 1–120 chars,
   - number: string, 1–40 chars,
   - label: string, 0–80 chars.
5. Receipt, sale detail, sales CSV, and KPay ledger rows display the snapshot when present.
6. Keep `kpayTransactionReference` validation unchanged.

### 8.4 Extend the same pattern (recommended, needs approval)

- **Customer payments (KPay):** snapshot the receiving account alongside the payer
  `senderAccountName/Number` already stored.
- **Cashier settlements (KPay):** snapshot the receiving account for the handover.
- **Manual KPay ledger entries:** snapshot the account active when the entry was created.

### 8.5 Affected files

- `src/store/usePosStore.ts` — `Sale` type and any customer-payment/settlement types.
- `src/App.tsx` — sale creation, receipt/copy, CSV.
- `src/lib/cashierSalesSync.ts` — payload construction and idempotency fingerprint.
- `src/components/CashierSettlementManagementPage.tsx`,
  `src/components/BranchFinanceManagementPage.tsx` — snapshots on new records.
- `firestore.rules` — optional field validation for cashier-created records.
- Tests: cashier sales sync, rules, KPay compliance.

### 8.6 Data compatibility and tests

- **Compatibility:** additive optional fields; no migration; no rewrite; old clients can
  still read sales without snapshots.
- **Rules tests:**
  - KPay sale with valid snapshot accepted.
  - Snapshot fields of wrong type/length rejected.
  - Offline-style sale whose snapshot differs from current settings accepted.
  - Legacy sale without snapshot still readable/updatable under existing rules.
- **Manual tests:**
  1. Owner sets KPay A → cashier sells → receipt shows A.
  2. Owner changes to KPay B → new sale shows B; old sale still shows A.
  3. Cashier offline → Owner changes account → cashier reconnects → queued sale commits
     with the account the cashier saw (A), not B.
  4. Cashier cannot reach the account-edit page or write branch settings.

## Appendix B — Cost formula notes

- `OwnerAutoSync` attaches one listener per branch per kind; `branchRecordKinds` has 21
  entries. Categories/products are required for immediate checkout; the other 19 include
  historical kinds.
- Incremental cursors reduce repeat reads but do not bound the **first** sync or a
  full-refresh/reset sync.
- `activityLogs` has no cursor path (it is not in `incrementalBranchKinds`) and is
  imported without the local 300-entry cap, so both cloud reads and local state grow.
- Cashier cash collections have no cursor or limit; their cost is a function of branch age.
- Per-sale transactions scale with changed products/batches; this is the integrity floor.
- Shop images never reach Firestore/Storage.

## Appendix C — Contrast methodology

Ratios use the WCAG 2.x relative-luminance formula with sRGB linearization. Values quoted
as "≈" are rounded to two decimals and should be re-verified in-browser after tokens are
implemented. Non-text UI boundaries (input borders, focus rings) are evaluated against the
3:1 non-text threshold.
