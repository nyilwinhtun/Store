## 1. Completed work

### P0 / C1 — Dangerous local reset, restore, and role-switch data loss

- Added `src/lib/syncSafety.ts` with persistent replacement markers, full-refresh flags, manifest supersession checks, and a cross-tab `storage` listener.
- `clearAllData()` now marks the replacement **before** mutating state, so the sync layer never publishes tombstones for an intentional local wipe.
- Payment restore / JSON import follows the same marker path.
- Owner ↔ Cashier session changes clear device data without deleting cloud records.
- Regression coverage: `tests/sync-safety.test.mjs` (7 tests).

### P1 — Financial security hardening (`firestore.rules`)

- Cashier expense writes are limited by the branch `settings.cashierExpenseApprovalLimit` (default 50,000).
- Sale `total` must equal `subtotal - discount`; cashier sale totals and stock deltas are reconciled server-side.
- Cash shift, movement, and customer payment payloads use strict key allowlists.
- Cash movements must reference an existing, open shift in the same branch.
- Customer payments must reference a completed Credit sale for the same customer and cannot exceed its remaining due.
- Credit-sale payment updates are monotonic: paid may only increase and due may only decrease, with `paid + due == total`.
- Shift close validates immutable opening fields, closing figures, and variance.
- Regression coverage: `tests/firestore.rules.test.mjs` (19 emulator tests).

### P1 — Durable cashier cash outbox

- New pure payload builders in `src/lib/cashierCashRecords.ts`.
- New transactional apply logic in `src/lib/cashierCashApply.ts`:
  - Shift open/close, cash movement, and customer credit payment are idempotent per record ID.
  - Conflicting Cloud state raises `failed-precondition` (review state) instead of overwriting.
  - Customer payments atomically update the Credit sale `paidAmount` / `dueAmount` and create the payment record.
- New FIFO queue in `src/lib/cashierCashSync.ts`, persisted in IndexedDB through the existing durable key/value layer:
  - Enqueue happens before any network attempt.
  - Web Locks serialize writers; in-flight flushes are deduplicated.
  - Offline records flush on reconnect, on mount, and after each enqueue.
  - Permanent conflicts are flagged for review; permission errors stop the queue; a missing Credit Sale is retried (bounded) so it can wait for the sale outbox.
  - Recovery is bounded to shifts from the last 7 days and movements of open shifts.
- `CashierAutoSync` now enqueues shifts, movements, and payments instead of fire-and-forget `setDoc`.
- Regression coverage: `tests/cashier-cash-records.test.mjs` (11) and `tests/cashier-cash-apply.test.mjs` (16) — 27 total, run with a deterministic in-memory Firestore double.

### P1 — Cashier query bounds and ordering

- Own sales, expenses, and settlements now subscribe with `orderBy(...)` + `limit(100)` so the bounded window holds the **newest** records instead of an arbitrary document-ID slice.
- If the composite index is not deployed yet, the listener catches `failed-precondition` and falls back to the legacy unordered query instead of losing sync.
- Required composite indexes are documented in `firestore.indexes.json` (not deployed).

### P2 — Sync baseline durability and diagnostics

- `saveManifest()` no longer throws when browser storage is full; it reports failure through `minimart-cloud-manifest-write-failed`.
- Owner sync surfaces baseline write failures as a visible sync error and keeps the Cloud data untouched.
- Conflict status now includes up to 20 conflicting record keys; the sync status card lists them so the owner can identify the records before exporting a backup.

### P2 — PWA update prompt

- The service worker now reports an installed update through `minimart-app-update-ready`.
- `AppUpdateBanner` shows a non-blocking, emerald banner with explicit **Update** and **Later** actions, so an in-progress cart is never reloaded automatically.
- The service worker cache name was bumped to `v326-financial-safety`; activation retires only Minimart-owned caches and never touches IndexedDB/LocalStorage business data.

### P2 — Independent code review fixes

- **Credit payment vs. sale queue race.** A cashier can record a Credit payment while the sale itself is still in the separate sale outbox. `applyCustomerPayment` now treats a missing Cloud sale as retryable for the first 5 attempts and only then asks for Owner review, instead of permanently flagging a healthy payment.
- **Reset during an in-flight owner push.** `writeItemsIfBaselineUnchanged` checks the replacement marker before every 400-document transaction chunk and aborts the remaining writes, so a reset/restore can no longer finish writing a pre-reset dataset (including deletions) to Cloud.
- **Bootstrap baseline honesty.** A Device bootstrap whose manifest cannot be persisted now fails with a storage error instead of reporting "synced" and leaving reconciliation without a baseline.
- **Cash queue integrity.** Queued entries are rejected before apply when the envelope `recordId`, embedded shift/movement/payment ID, or embedded branch disagree with the queue entry. Customer payments are also validated at enqueue time (branch, sale ID, settlement figures).

### Performance — Chunk splitting

- `vite.config.ts` now emits stable `vendor-firebase`, `vendor-react`, and `vendor-icons` chunks.
- Modules used only by lazy routes (barcode scanner) stay inside their route chunk; they are **not** pulled into the initial payload.
- `scripts/bundle-report.mjs` now counts statically imported vendor chunks in the initial payload and labels them `[VENDOR]` instead of mislabelling them as lazy.

## 4. Known limitations

1. **Cross-device payment duplication.** Two devices paying the same Credit sale concurrently are protected by the expected-state check and the Rules' due cap, but a fully authoritative duplicate guard needs a Cloud Function callable. Current behavior is fail-safe: the second device gets a review error instead of a double payment.
2. **Composite indexes are not deployed.** Cashier lists fall back to the unordered query until `firebase deploy --only firestore:indexes` is run with authorization.
3. **Baseline hash is FNV-1a 32-bit.** It is a change detector, not a cryptographic hash. A SHA-256 migration requires an async manifest version bump and is intentionally deferred.
4. **Manifest storage.** The baseline still lives in LocalStorage; quota failures are now visible but the baseline is not mirrored to IndexedDB.
5. **Sync conflicts halt reconciliation.** Conflicting record keys are now shown, but there is no per-record "keep Cloud" / "keep device" resolver yet. The safe procedure remains: export a JSON backup, compare the records, then re-run sync.
6. **Cursor skew.** Incremental cursors use client-written `updatedAt` values with a 120-second overlap. Server timestamps are not yet used.
7. **Cash recovery window.** Cash-outbox recovery only scans shifts from the last 7 days and own records; older pending records must be re-created or synced manually. Recovery also does not rebuild customer-payment entries (their pre-payment balance cannot be reconstructed safely from local state).
8. **Cash movements on another cashier's shift.** The Rules require an open shift in the same branch but not the same `openedByUid`; legacy shifts without an opener UID make a stricter rule unsafe to add.
9. **Emulator transactions.** `runTransaction` commits hang under the local Node v27 alpha + Firebase 13.2 combination. Apply logic is covered by a deterministic fake-Firestore harness instead.
10. **Not implemented yet:** App Check / rate limiting, manager role, returns/refunds, damaged-stock workflow, report pagination, SHA-256 manifest, per-record conflict resolution.

## 5. Release notes (draft)

**v3.2.6 — Financial safety and offline reliability**

- Cashier shifts, cash movements, and customer credit payments are now queued durably in IndexedDB and retried in order; offline records survive browser restarts.
- Credit payments update the sale balance atomically and are safe to replay.
- Firestore Rules now enforce expense approval limits, sale total reconciliation, cash payload allowlists, open-shift linkage, and monotonic credit payments.
- Local reset / restore / role switch can no longer delete cloud records.
- Cashier sales, expenses, and settlements load the newest 100 records.
- Sync baseline failures (full browser storage) are surfaced instead of failing silently; conflicting record names are listed.
- A Credit payment that reaches Cloud before its offline sale now retries instead of asking the Owner to review it.
- Smaller app entry bundle (1.29 MB → 340 KB) with cacheable Firebase/React vendor chunks.
