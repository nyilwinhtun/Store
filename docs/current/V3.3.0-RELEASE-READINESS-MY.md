## 6. Remaining known limitations

1. Production authenticated pages were not reviewed in this session. In the
   emulator, login plus the customer credit statement were exercised; other
   Owner pages were reviewed only through code and global theme tokens, so
   layout regressions on production data remain possible.
2. No device, printer, scanner or real KPay flow was exercised.
3. Cloud read/write savings cannot be measured without Firebase Console access;
   listener counters were added so on-device diagnostics can confirm them.
4. ~22 dense finance/operations tables keep horizontal scroll on mobile.
5. Archived-branch records deleted directly in the console are not purged from
   an already-synced cashier device; no app workflow deletes them.
6. Legacy sales without a cashier UID are hidden from cashier history by design.
7. KPay QR camera round-trip was not tested on a physical phone.
8. The visible app version label still reads `v3.2.5 DATA RELIABILITY`; choosing
   the public release number (v3.2.6 vs v3.3.0) and updating the label is an
   Owner decision. The service-worker cache is already `v326-financial-safety`.
9. Emulator data lives in memory and is recreated by `npm run seed:emulator` on
   every emulator start. It is a safety harness, not durable staging; no cloud
   staging project, Blaze plan or Functions deployment was created.
10. Statement printing was verified as a print-time DOM snapshot plus compiled
    `@media print` rules (58 mm and 80 mm). Physical paper output, printer
    scaling and Android WebView print-dialog margins are UNVERIFIED. Mobile share
    uses `navigator.share` when available and falls back to copy; the native
    share sheet was not exercised.
11. A-04 (KPay QR on the receipt) is deferred by Owner decision; receipts keep
    the frozen account name/number and the payment screen keeps the QR.
12. The pre-existing duplicate category-name list key warning remains in the
    console; it is unrelated to the new work and was not introduced here.

## 7. Local startup

```bash
# Node.js >= 24.12.0
npm install
npm --prefix functions install

# development (production Firebase config, no emulator)
npm run dev            # Vite dev server

# safe emulator environment (demo-minimart-staging)
npm run emulators      # Auth 9099, Firestore 8099, Functions 5001 (Functions built first)
npm run seed:emulator  # synthetic accounts + Myanmar retail data, run in a second terminal
npm run dev:emulator   # Vite --mode emulator, EMULATOR badge, fail-closed guard

# verification
npm run typecheck
npm run qa:quick       # unit suites + build, no emulator required
npm run qa             # full QA incl. Firestore emulator rules on port 8099 (Java 21+)
npm run test:overview  # branch aggregation + benchmark
npm run test:runtime   # fail-closed Firebase runtime resolution
npm run test:statement # customer credit statement engine
npm run test:checkout  # POS layout contract, KPay reference gate, duplicate-tap lock

# production bundle (local only)
npm run build
npm run preview
```

Firebase: the app reads its config from the existing source. `npm run dev` keeps
the production project ID; `npm run dev:emulator` refuses to start against
`minimart-production` and binds the demo project to the local emulators instead.
Emulator credentials are synthetic; the seeded Owner (`bonyiontheway@gmail.com`)
and cashier passwords exist only in the local emulator and are stored in
`/Users/user/Documents/GitHub/Store-backups/emulator-credentials.local.txt`
(outside the repository, mode 600). They are never written to logs, source or
documentation. Rules/Functions are tested only in the emulator. Do not run
`firebase deploy` without separate authorization.
