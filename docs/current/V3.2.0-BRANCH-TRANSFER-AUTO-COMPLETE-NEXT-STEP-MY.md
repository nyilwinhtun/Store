# Branch Transfer Exception-Only Auto Complete — Technical Plan

## User-approved operating rule

- Normal receipt: dispatched quantity == received quantity and damaged quantity == 0. The destination stock should be committed automatically after the receiver confirms.
- Exception: missing quantity, extra quantity (must remain blocked unless explicitly reconciled), damaged quantity, or a product/barcode mismatch. The shipment remains pending Owner review.
- The source shipment and full audit history must remain immutable/traceable. Repeated submit must not add stock twice.

## Why Preview 2 does not turn on Auto Complete yet

The current Cashier receive transaction updates only the destination branch's `stockShipments` document to `status: received`. Current Firestore Rules intentionally restrict that Cashier update to receipt fields and do not let a Cashier also create/update destination `products` and `stockBatches`. The existing Owner `approveBranchStockShipment` is the only code path that adds the destination stock.

Changing the UI to display `approved` without committing destination Product/Batch records would make the stock totals wrong. Relaxing Rules broadly would allow a compromised Cashier session to alter inventory. Neither shortcut is acceptable.

## Required secure implementation

1. Add a dedicated Cloud transaction for receiver completion.
2. Read the destination `stockShipments/{shipmentId}` and verify it is still `dispatched`, the receiver UID belongs to the exact destination Branch, and the member has `canReceiveStock == true`.
3. Read all destination Product and Stock Batch documents before writing. Reuse the same SKU / barcode / name+unit matching and weighted-cost / batch-allocation rules as the current Owner approval path.
4. If every line exactly matches dispatched quantity and damage is zero, atomically write destination Product/Batch stock, shipment completion status, receiver actor/time and audit record.
5. If any mismatch is present, only save the receipt evidence and mark it as an Owner-review exception. Do not add uncertain quantities to sellable stock.
6. Add idempotency: the transaction must only run while the shipment is `dispatched`; replays must return the existing committed result and never increment stock twice.
7. Update Firestore Rules with narrowly scoped validations that link every permitted destination stock write to the exact matching shipment and receipt, and test with the Firebase Emulator. Do not grant generic Cashier Product/Stock write permissions.
8. Test transaction access-call limits, batch sizes, existing Product match, new Product creation, multiple batches, retries, offline failure, duplicate receive, and concurrent receiving.
9. Preserve existing Owner approval for exceptions, cancellation before receive, and all legacy shipment history.

## Release gate

Do not enable the automatic path in Production until Firestore Emulator tests pass for both allowed exact-match receipts and rejected/exception receipts. If the current Firebase plan / Rules design cannot safely support it, keep Owner approval as the safe fallback rather than bypassing Rules.
