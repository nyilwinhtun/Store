## 0. Planning principles

1. **Preserve first.** Every KEEP item below is a release blocker if changed without
   explicit approval.
2. **Additive data only.** New fields are optional; no destructive migration; no
   backfilling of historical facts.
3. **Offline-first is non-negotiable.** IndexedDB persistence and cashier outboxes stay.
4. **Financial integrity is non-negotiable.** Per-sale transactions, stock/batch
   validation, and Rules reconciliation stay.
5. **No production deployment.** Staging/emulator only until separate authorization.
6. **No invented metrics.** Cost and performance numbers are estimates with stated
   assumptions; real values come from the Firebase Console and device profiling.
7. **One phase at a time.** Each phase has a gate; do not start the next phase until the
   previous gate passes.

### 7.2 KPay branch-specific account management

**Owner-editable, cashier read-only:**

- Current fields: `kpayAccountName`, `kpayAccountNumber`, `kpayAccountLabel`.
- Add: `kpayQrDataUrl`, `kpayQrVersion`, `kpayQrUpdatedAt`, `kpayQrUpdatedBy`.
- Owner can change any of these at any time.
- Cashier can only read them through the branch document; Rules already make branch
  writes Owner-only.
- Every KPay sale stores the account name/number/label used at sale time.
- Every KPay sale stores `kpayQrVersionSnapshot` (small integer), not the QR image.
- Legacy KPay sales show "not recorded" — never the current account.
- Account changes create an audit entry (`KPAY_ACCOUNT_UPDATE`) with old/new
  name/number/label and actor/time (no QR blob).
- Offline cashier behavior: the snapshot is taken from the branch settings the cashier
  saw at sale time. Rules must **not** require equality with the current branch settings.

### 7.3 Firebase cost optimization

| Action | Expected effect | Guardrail |
|---|---|---|
| Bound `activityLogs` sync (X-03) | 60–90% lower Owner cold-start reads in mature shops | Keep cloud history; on-demand pagination |
| Manifest to IndexedDB (X-02) | Remove 21×N parses and 5 MB ceiling | Atomic baseline; no push without baseline |
| Bound cashier cash collections (X-04) | 50–85% lower cashier cold reads in older branches | Only after ledger-equivalence proof |
| Exclude archived branches (X-05) | 30–70% fewer listeners after consolidation | Archived data remains restorable |
| Metadata callbacks off (X-06) | Lower CPU/churn | Pending-write state preserved |
| Keep per-sale transactions | No change | Financial integrity |

- Do not change billing plans or production data.
- Budget alerts notify; they do not cap spending.
- Measure before/after with Console + `firestoreDiagnostics` on a seeded dataset.
- Spark's 50k reads/day cap is already incompatible with blocking Auth functions
  (Blaze + Identity Platform required). This is an operational fact, not a task.

### 7.4 Offline-first operation

- Keep IndexedDB state, outbox, Web Locks, and idempotent transactions.
- New snapshot/QR fields must be available offline from the cached branch document.
- No new feature may require a live Firestore read to complete a sale.
- Test: airplane mode, tab kill, browser restart, reconnect, duplicate replay.

### 7.5 Existing data protection

- All Firestore changes are additive and optional.
- No production migration, no destructive rewrite, no backfill.
- Manifest migration must be dual-read/atomic with a rollback path.
- Activity-log sync changes must not delete cloud documents.
- Archived-branch sync exclusion must not delete archived documents.
- Cashier bounds must preserve ledger totals and opening balances.
- Before/after JSON backup and restore test is mandatory.

### 7.6 Professional Emerald UI redesign

- Direction: **Vibrant Emerald evolution** (full token table in the audit, Section 6).
- Phase 4 implements tokens, component states, contrast, light/dark, typography, touch.
- Keep application branding separate from shop logo/banner data.
- No new heavy assets; SVG/CSS only.

### 7.7 Animated login icon

- Phase 3: CSS ring spinner, subtle icon glow, success check, no shake.
- Respect `prefers-reduced-motion` (existing global rule).
- No auth logic or validation changes.

### 7.8 Modern light and dark themes

- Phase 4: full light/dark token sets; system preference plus existing manual toggle;
  no flash (existing `index.html` bootstrap); contrast check on both themes.
- Dark mode must cover inputs, tables, dialogs, QR panel, alerts, and disabled states.

### 7.9 Performance optimization

- Phase 5: product virtualization, Branch Overview aggregation, mobile tables, lazy
  fallbacks, object-URL cleanup, bundle check.
- Cost-related performance is Phase 2; UI render performance is Phase 5.
- No Firestore write per keystroke; search remains local.

## 10. Data model changes summary

- Existing Firestore collection paths.
- Existing LocalStorage keys remain readable during migration.
