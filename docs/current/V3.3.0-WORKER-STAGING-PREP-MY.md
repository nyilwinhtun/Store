## 2. Firebase Console — အတိအကျ အဆင့်များ

1. https://console.firebase.google.com/ သို့ Owner အကောင့်ဖြင့် ဝင်ပါ။
2. **Add project** → အမည် `minimart-staging` (သို့မဟုတ် သီးခြား ကိုယ်ပိုင်အမည်) ပေးပါ။
3. **Continue** စဉ်တွင် **Google Analytics ကို ပိတ်ပါ** (မလိုအပ်ပါ)။
4. Billing အဆင့်တွင် **Spark (Free)** ကိုသာ ရွေးပါ။ **Blaze သို့ မတင်ပါ**။
5. Project အသစ်ထဲတွင် **Build → Firestore Database → Create database** ကို နှိပ်ပါ။
   - **Native mode** ရွေးပါ။
   - Location ကို production နှင့် မတူဘဲ သီးခြားရွေးပါ (ဥပမာ `asia-southeast1`)။
   - Test mode ကို ရှေးရှု မရွေးပါနှင့်။ Rules ကို နောက်မှ သီးခြား စစ်ဆေးမည်။
6. **Build → Authentication → Get started → Sign-in method → Email/Password → Enable** လုပ်ပါ။
7. **Project settings → General → Your apps → Web app** ဖြင့် Staging web app တစ်ခု ဖန်တီးပါ။
   (ဤသည် public client config သာ ဖြစ်သည်။ APK မလုပ်ပါ။)
8. **Project settings → Service accounts → Generate new private key** ကို နှိပ်ပါ။
   - ရလာသော JSON ကို **chat, source code, Git, screenshot, log ထဲ မထည့်ပါ**။
   - Terminal မှတစ်ဆင့် Cloudflare Secret အဖြစ် တိုက်ရိုက် ထည့်ပါ။

## 3. အနည်းဆုံး IAM Permission

Worker service account အတွက် အောက်ပါ roles နှစ်ခုသာ လုံလောက်ပါသည်။
`Owner`, `Editor`, `Firebase Admin` မပေးပါနှင့်။

| Role | ဘာအတွက် |
| --- | --- |
| `roles/datastore.user` | Firestore REST transaction read/write |
| `roles/firebaseauth.viewer` | `accounts:lookup` ဖြင့် token revocation (`validSince`) စစ်ဆေးရန် |

Service account သည် Firestore Rules ကို ကျော်ဖြတ်သည်။ ထို့ကြောင့် Worker
ကုဒ်ထဲရှိ authorization စစ်ဆေးမှုများ (role/branch/membership/device/lease)
သည် မဖြစ်မနေ လိုအပ်သည်။ Role များကို ပိုမပေးပါနှင့်။

### 3.1 Spark တွင် Service Account ရနိုင်မှု စစ်ဆေးချက်

- Firebase Console → **Project settings → Service accounts → Generate new private key**
  သည် Spark project တွင် အသုံးပြုနိုင်သည်။ Billing account မလိုအပ်ပါ။
  Owner က Console တွင် ကိုယ်တိုင် အတည်ပြုပါ။
- Key ကို generate လုပ်ပြီးနောက် **IAM & Admin → IAM** တွင် service account
  အတွက် အောက်ပါ role နှစ်ခုသာ ရှိကြောင်း စစ်ပါ။
- Role ပေးရန် (Owner ၏ ကိုယ်ပိုင် terminal; `gcloud` မရှိလျှင် Console → IAM →
  Grant access ကို သုံးပါ) —

```bash
gcloud projects add-iam-policy-binding REPLACE_WITH_STAGING_PROJECT_ID \
  --member="serviceAccount:REPLACE_WITH_STAGING_SA_EMAIL" \
  --role="roles/datastore.user"

gcloud projects add-iam-policy-binding REPLACE_WITH_STAGING_PROJECT_ID \
  --member="serviceAccount:REPLACE_WITH_STAGING_SA_EMAIL" \
  --role="roles/firebaseauth.viewer"
```

- `roles/firebaseauth.viewer` သည် `accounts:lookup` (token revocation `validSince`)
  အတွက်သာ ဖြစ်သည်။ 403 ရလျှင် Admin role မပေးဘဲ ရပ်ပြီး အစီရင်ခံပါ။
- Project Owner/Editor၊ `roles/firebase.admin` မပေးပါနှင့်။
- Blaze မဖွင့်ပါ။ Billing account မချိတ်ပါ။

### 3.2 Isolated Staging Fixture

- Template: `experiments/cloudflare-workers-spark-poc/staging.fixture.example.json`
- Staging business ID ကို `store-staging-main` ဟု သီးခြားထားပြီး
  Production `store-mini-main` နှင့် မရောပါ။
- Owner နှင့် Cashier အကောင့်များကို Staging Console → Authentication တွင်
  ကိုယ်တိုင် ဖန်တီးပြီး UID/email ကို fixture ထဲ အစားထိုးပါ။ Password ကို
  fixture၊ Git၊ chat ထဲ မထည့်ပါ။
- Completed fixture ကို Git ပြင်ပ (ဥပမာ `Store-backups/`) တွင် သိမ်းပါ။
- အောက်ပါ preflight ကို run ပါ —

```bash
PATH=/tmp/node24/bin:$PATH npm run check:staging
```

Preflight သည် အောက်ပါအချက်များကို စစ်သည် — Staging config တွင် Production
project/business မပါခြင်း၊ `minimart-staging` / `store-staging-main` အတိအကျ
ဖြစ်ခြင်း၊ `ENVIRONMENT = "staging"` ပါခြင်း၊ secret မပါခြင်း၊
`wrangler.staging.toml` Git-ignore ဖြစ်ခြင်း၊ Production Worker
`workers_dev = false` ဖြစ်ခြင်း၊ Worker client default disabled ဖြစ်ခြင်း၊
repo ထဲ service-account material မရှိခြင်း။

## 4. Credential ထည့်သွင်းမှု — လုံခြုံသော နည်းလမ်း

Owner ၏ ကိုယ်ပိုင် terminal တွင်သာ လုပ်ပါ။ ဤ chat ထဲသို့ key မကူးယူပါနှင့်။

```bash
cd /path/to/Store/experiments/cloudflare-workers-spark-poc

# 1) Key ကို ကိုယ်ပိုင် Downloads folder မှ terminal ဖြင့် တိုက်ရိုက် ဖတ်ပါ။
#    ဤ command သည် key ကို screen/log ထဲ မပြပါ။
#    --config မပါဘဲ မ run ရ — default wrangler.toml သို့ secret တင်မိမည်။
npx wrangler secret put FIRESTORE_SERVICE_ACCOUNT \
  --config wrangler.staging.toml \
  < "$HOME/Downloads/minimart-staging-service-account.json"

# 2) Secret ထည့်ပြီးပါက key file ကို ဖျက်ပါ (macOS secure overwrite)။
rm -P "$HOME/Downloads/minimart-staging-service-account.json"
```

မလုပ်ရ:

- Key ကို `wrangler.toml`, `.dev.vars`, `.env`, Git, APK, browser bundle ထဲ မထည့်ပါ။
- Key ကို chat/ChatGPT/screenshot/email ထဲ မကူးပါ။
- Key ကို shell history ထဲ မထည့်ပါ။ အထက်ပါ `< file` နည်းလမ်းက history ထဲ key မထည့်ပါ။

## 5. Staging Deploy အတွက် ပြင်ဆင်ထားသော Command များ (မ run ရသေးပါ)

`wrangler.staging.toml` ကို `minimart-staging` / `store-staging-main` ဖြင့်
local တွင် ပြင်ဆင်ပြီးဖြစ်သည် (Git-ignored)။ Deploy မလုပ်မီ အကြောင်းအရာကို
ပြန်စစ်ပါ။ Runtime guard သည် `ENVIRONMENT=staging` ဖြစ်လျှင် Production
project/business ကို ငြင်းပယ်ပြီး service account ၏ `project_id` မကိုက်ညီလျှင်
credential အဆင့်တွင် ငြင်းပယ်သည်။ ထို့နောက်:

```bash
cd /path/to/Store/experiments/cloudflare-workers-spark-poc

# Free plan only; no routes, no paid features.
npx wrangler deploy --config wrangler.staging.toml

# Set the web build endpoint (Staging only; do not point at production):
# VITE_WORKER_SALES_ENABLED=true
# VITE_WORKER_SALES_URL=https://<staging-worker>.workers.dev
```

Deploy မလုပ်မီ အတည်ပြုရန်:

- Firebase Console တွင် project သည် **Spark** ဖြစ်နေကြောင်း။
- Billing account မချိတ်ထားကြောင်း။
- Cloudflare account သည် **Workers Free** ဖြစ်ကြောင်း။
- `FIRESTORE_SERVICE_ACCOUNT` သည် Staging project ၏ key ဖြစ်ကြောင်း (production key မဟုတ်)။
- `wrangler.staging.toml` ကို Git သို့ မထည့်ထားကြောင်း။

## 6. Owner ခွင့်ပြုချက် ရပြီးနောက် စမ်းသပ်မည့် Matrix

ဤစာရင်းကို အမှန်တကယ် run ပြီးမှသာ "Staging passed" ဟု ဆိုမည်။

1. Real Firebase ID token verification (Owner/Cashier အကောင့်အစစ်)။
2. Worker auth + role/branch/membership/branch status။
3. Firestore REST transaction (single atomic commit)။
4. 1/5/10/20-line sales။
5. Duplicate barcode / duplicate unit; duplicate sale retry → `already-committed`။
6. Concurrent sale of the same unit and same limited stock။
7. Cash / KPay / Credit (KPay reference reuse)။
8. Token revocation (`validSince`) နှင့် disabled Cashier။
9. Server-issued 24-hour allowance: 23h accepted, exactly 24h expired, 25h held။
10. Server-issued 72-hour lease: 71h valid, exactly 72h expired, 73h rejected။
11. Device clock နောက်ပြန်ရွှေ့ခြင်းက allowance ကို မတိုးစေကြောင်း။
12. Expired allowance က stock ကို အလိုအလျောက် မလွှတ်ကြောင်း; Owner reconcile ဖြင့်သာ လွှတ်ကြောင်း။
13. workerd CPU / memory / subrequest / payload / latency တိုင်းတာမှု။
14. Cashier Void: synced Sale ကို Void လုပ်ပြီး Product / Batch / Unit Registry
    ပြန်တိုးမှု၊ Audit Record၊ တူညီသော Request ID ဖြင့် Retry လုပ်လျှင်
    `already-committed` သာ ပြန်လာပြီး Stock နှစ်ကြိမ် မတိုးမှု။
15. Cashier Return: Saleable Unit သာ Restock လုပ်မှု၊ Damaged Unit ကို
    `damaged` အဖြစ် Quarantine လုပ်မှု၊ Over-return / ထပ်ခါ Unit Return ကို
    ငြင်းပယ်မှု၊ Return ပြီးသား Sale ကို Void မရမှု။
16. KPay Return သည် `kpay-pending` ဟု ရိုးသားစွာ မှတ်တမ်းတင်မှု၊ Credit Return
    သည် ကျန်ရှိ Due ကို လျှော့ချပြီး ပိုငွေကို `credit-refund-review` ဟု
    သတ်မှတ်မှု။
17. Worker `/api/sales/void` နှင့် `/api/sales/return` အတွက် Role/Branch/
    Disabled Cashier Authorization ကို စစ်ဆေးမှု။
18. မတူညီသော Quantity များ၊ Batch များစွာ၊ Insufficient stock၊ Expired batch၊
    Client ပေးသော မှားသော Price/Subtotal တို့ကို Server-side ငြင်းပယ်မှု။
19. Sale ID တူပြီး Payload မတူညီသော Retry ကို ငြင်းပယ်မှု။
20. Server commit ပြီးနောက် Network timeout ဖြစ်လျှင် Retry တစ်ကြိမ်တည်း
    သာ Cloud Sale ဖြစ်မှု။
21. Concurrent Cashier နှစ်ဦး တူညီသော Barcode/stock ကို တပြိုင်နက်
    ရောင်းချမှု ကာကွယ်မှု။

Scenario တစ်ခုစီအတွက် အောက်ပါတို့ကို မှတ်တမ်းတင်ရမည် — ရလဒ်၊ Firestore reads၊
Firestore writes၊ Worker subrequests၊ HTTP response၊ partial write ဖြစ်မဖြစ်။

Local-only အထောက်အထား —

- `npm run test:sale-adjustments-server` — Cloud Functions Void/Return 11 checks PASS။
- `npm --prefix experiments/cloudflare-workers-spark-poc test` — Worker POC 70 tests PASS
  (အသစ်ထည့်ထားသော Void 3 နှင့် Return 3 scenarios အပါအဝင်)။
- ဤရလဒ်များသည် Emulator ပေါ်တွင်သာ ဖြစ်ပြီး Cloud Staging ဟု မခေါ်ရပါ။

## 7. ရပ်တန့်ရမည့် အချက်

ဤစာရွက်စာတမ်းသည် ပြင်ဆင်မှုသာ ဖြစ်သည်။ အောက်ပါအချက်များ မပြည့်မီ
Staging deploy သို့မဟုတ် checkout integration ကို မဆက်လုပ်ပါ:

- Owner မှ Staging project ဖန်တီးပြီး အတည်ပြုချက် ပေးခြင်း။
- Owner မှ service-account credential ကို ကိုယ်တိုင် terminal မှ ထည့်ခြင်း။
- Staging အတွက် သီးခြား Rules/indexes ကို စစ်ဆေးခြင်း။
- ဤ repo တွင် Production Rules/ဒေတာများ မပြောင်းလဲကြောင်း အတည်ပြုခြင်း။
