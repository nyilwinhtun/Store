## 3. Confirmed application permission failures under the deployed Rules

These are confirmed by comparing the live rule predicates with the current
application queries and writes. They affect the deployed v3.3.0 client, not the
local Rules.

### F1 — Every Cashier sale fails, for every payment method (critical)

- App: `src/lib/cashierSalesSync.ts:284-285` always writes
  `saleFingerprint` and `cashierSyncVersion: 2`; `:403` writes the
  `${sale.id}__created` audit event in the same transaction.
- Deployed: line 180 requires `cashierSyncVersion == 1`.
- Impact: Cash and Credit sales are denied too, not only KPay. The device
  records the sale locally and decrements local stock, but the cloud write is
  permanently rejected; the Owner never sees the sale, and cloud/local stock
  diverge.
- Classification: confirmed defect.

### F2 — KPay checkout (critical)

- App: `src/App.tsx:102` allows `KPay`; `:633` gates it on branch KPay; `:703`
  writes `kpayTransactionReference`.
- Deployed: line 172 permits only `Cash` and `Credit`; there is no
  `branchHasConfiguredKPay` check or KPay snapshot fields.
- Impact: KPay sales cannot sync under any circumstance.
- Classification: confirmed defect.

### F3 — Cashier expense and settlement history (high)

- App: `src/components/CashierAutoSync.tsx:392-402` opens own-record listeners
  with `where('payload.createdByUid' == uid)` / `where('payload.cashierUid' == uid)`
  and `limit(100)`; `:357-359` applies the same bound.
- Deployed: lines 326-332 allow Cashier list only for categories, products,
  stockBatches, shipments and own sales. `expenses` and `cashierSettlements`
  have no Cashier list or get branch.
- Impact: permission-denied listeners; the Cashier loses own expense and
  settlement history, and the UI shows the Rules warning.
- Classification: confirmed defect.

### F4 — Customer credit collection (high)

- App: `src/lib/cashierCashApply.ts:157` writes `customerPayments`; `:205-211`
  updates the Credit sale `paidAmount`/`dueAmount` in the same transaction.
- Deployed: line 334-337 has no Cashier create for `customerPayments`; lines
  339-342 have no Cashier sale update.
- Impact: the payment stays queued; due balances and Owner statements remain
  stale while the device shows the payment as recorded.
- Classification: confirmed defect.

### F5 — Cash shift, cash movement and payment listeners (high)

- App: `src/components/CashierAutoSync.tsx:295-300` attaches listeners for
  `cashShifts`, `cashMovements` and `customerPayments`.
- Deployed: these collections are absent from both Cashier get (314-324) and
  list (326-332).
- Impact: permission-denied listeners; shift state and payment history do not
  sync.
- Classification: confirmed defect.

### F6 — Shared customer directory list (medium)

- App: `src/components/CashierAutoSync.tsx:303-309` lists
  `shared/customers/records`.
- Deployed: line 354 allows `list` only to the Owner; `get` at 353 is allowed.
- Impact: the customer list does not sync; credit customer selection depends on
  previously cached data. The listener currently swallows the error.
- Classification: confirmed defect.

### F7 — Stock and batch updates inside the sale transaction (critical, tied to F1)

- App: `src/lib/cashierSalesSync.ts:214` commits sale, product and batch
  updates atomically with `sourceSaleId`.
- Deployed: product/batch updates (185-218, 220-253) require the linked sale to
  satisfy the v1 envelope. Since the sale is rejected, the whole transaction is
  rejected.
- Classification: confirmed defect, resolved by the same fix as F1.

### F8 — Audit event (critical, tied to F1)

- App: `src/lib/cashierSalesSync.ts:403` writes the `SALE_CREATED` audit event.
- Deployed: audit create (88-111) requires `existsAfter` the v1-compliant sale.
- Classification: confirmed defect, resolved by the same fix as F1.

### Behaviour that remains valid under deployed Rules

- Owner login, business read, member and branch management.
- Cashier branch/product/category read and own sales history.
- Authorized receiver shipment acknowledgement.
- Shared customer `get` (but not `list`).
- Legacy `posAccounts` records (user-private).

### Deployment risk introduced by the stricter local rules

Local `isActiveMember` requires `request.auth.token.email`, a matching
`members/{uid}.email`, role `cashier`, exactly one branch, and an active Branch
document. Existing production member and branch documents were **not** dumped
or inspected beyond the Owner verification above. Before deployment, the Owner
must confirm that every active Cashier member has an email and exactly one
active branch, and that each assigned Branch document has
`payload.status == 'active'`. Otherwise that Cashier will be locked out.

## 4. Security risks and disposition

| Risk | Status |
|---|---|
| Deployed shared `get` exposes Price Groups and Suppliers to any active member | Confirmed in deployed; fixed locally (Owner-only) |
| Deployed member check ignores email, role and branch | Confirmed in deployed; fixed locally |
| KPay enable flag is not enforced in Rules | Accepted: preventing queued offline KPay sales from being rejected after the Owner disables KPay; UI enforces the flag |
| Queued KPay sale is rejected if the Branch KPay account is cleared before the sale syncs | Potential operational risk: the local rule requires a currently configured account. The UI blocks new KPay sales when disabled; existing queue retries indefinitely. Mitigation: do not clear the Branch KPay account while a Cashier has unsynced KPay sales, or flag the queue entry for Owner review. Not changed in this review. |
| Cashier sale audit is not mandatory in Rules | Accepted residual: the app always writes it; making it mandatory complicates idempotent retries |
| Product stock update is not mandatory for every delta | Accepted residual: a modified client could omit a reduction, but cannot increase stock or touch other branches |
| Item line totals are not cross-checked against `subtotal` | Accepted integrity risk: the app computes both; Rules cannot cheaply sum an item list. A modified client could under-report a sale. |
| `productDeltas` are not cross-checked against item quantities | Accepted integrity risk for the same reason; stock can only decrease and never cross branches |
| Cash shift close is branch-scoped, not opener-scoped | Potential: any Cashier in the same branch can close a shift opened by another Cashier. Tightening this could break Owner-opened shifts, so it is not changed in this review. |
| Cashier can record a credit payment on another Cashier's sale | Accepted: needed so any Cashier on shift can collect; sale listing remains own-only |
| Shared customer create payload is less strict than v3.0.0 | Accepted residual: create-only, cannot overwrite existing customers |
| Query bounds raised from 100 to 500 for own lists | Cost risk only; the app still requests 100 |
| Local relies on immutable `ownerUid` instead of the hard pin | Verified live; `ownerUid` update is blocked by Rules |
| `branchFinanceReconciliations` Owner update/delete blocked | Intentional append-only finance control; verify no app workflow updates these records |
| Cross-Cashier sale `get` within the same branch | Intentional: any Cashier must be able to collect a credit payment on a branch invoice; list remains own-only |
