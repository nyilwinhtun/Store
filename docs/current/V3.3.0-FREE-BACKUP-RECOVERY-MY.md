# V3.3.0 — Free-only Firestore Backup and Recovery Plan

> Owner ခွင့်ပြုချက် မရှိဘဲ Production ဒေတာကို ဖတ်/Export မလုပ်ရပါ။
> ဤ run တွင် Production ဒေတာ မဖတ်ပါ၊ မ Export ပါ။ Emulator ပေါ်တွင်သာ စမ်းသပ်ပြီးပါသည်။

နေ့စွဲ: 2026-11-15
အခြေအနေ: **Free-only tool နှင့် လုပ်ငန်းစဉ် အသင့်ဖြစ်ပြီး; စစ်မှန်သော Production backup မရှိသေးပါ။**

## 1. ဘာရှိပြီးသနည်း

| tool | ဖိုင် | အလုပ် |
| --- | --- | --- |
| Export | `scripts/firestore-export.mjs` | REST API ဖြင့် collection/subcollection အားလုံးကို NDJSON အဖြစ် ဆွဲထုတ်သည်။ Pagination ရှိသည်။ |
| Restore | `scripts/firestore-restore.mjs` | NDJSON ကို သတ်မှတ် project (Staging/Emulator) သို့ batch commit ဖြင့် ပြန်ထည့်သည်။ |
| Shared client | `scripts/firestoreRestClient.mjs` | Service-account token (server-side only) နှင့် REST helper။ Token/key ကို log မထုတ်ပါ။ |
| Test | `scripts/test-firestore-backup.mjs` | Emulator ပေါ်တွင် export → clear → restore round-trip နှင့် Production guard ကို စမ်းသည်။ |

## 2. Command များ

### Emulator (စမ်းသပ်ရန်)

```bash
PATH=/tmp/node24/bin:$PATH npm run test:backup
```

### စစ်မှန်သော Project (Owner ခွင့်ပြုချက် ရပြီးမှ)

Service-account key ကို Cloudflare secret အဖြစ် မထည့်ပါနှင့်။ ဤ tool အတွက်
local terminal တွင်သာ ခဏသုံးပြီး ချက်ချင်း ဖျက်ပါ။ Key ကို chat/Git/log ထဲ
မထည့်ပါ။

```bash
cd /Users/user/Documents/GitHub/Store

# Staging သို့ ပြန်ထည့်ရန် export (Staging key)
PATH=/tmp/node24/bin:$PATH node scripts/firestore-export.mjs \
  --project minimart-staging \
  --service-account "$HOME/Downloads/minimart-staging-service-account.json" \
  --out "$HOME/Documents/GitHub/Store-backups/staging-2026-11-15"

# Staging သို့ restore
PATH=/tmp/node24/bin:$PATH node scripts/firestore-restore.mjs \
  --project minimart-staging \
  --service-account "$HOME/Downloads/minimart-staging-service-account.json" \
  --in "$HOME/Documents/GitHub/Store-backups/staging-2026-11-15"

# Key ကို ချက်ချင်း ဖျက်ပါ
rm -P "$HOME/Downloads/minimart-staging-service-account.json"
```

Production export သည် နောက်ထပ် flag နှစ်ခု လိုအပ်သည် —

```bash
PATH=/tmp/node24/bin:$PATH node scripts/firestore-export.mjs \
  --project minimart-production --allow-production \
  --service-account "$HOME/Downloads/minimart-production-backup-key.json" \
  --out "$HOME/Documents/GitHub/Store-backups/production-2026-11-15"
```

`--allow-production` မပါလျှင် tool သည် ချက်ချင်း ရပ်ပြီး ဘာမှ မဖတ်ပါ။
`minimart-production` သို့ restore လုပ်ခြင်းကို အရေးပေါ် အခြေအနေတွင်သာ
Owner ၏ စာဖြင့် ခွင့်ပြုချက်နှင့် လုပ်ရမည်။ ပုံမှန် ပြန်လည်စမ်းသပ်မှုကို
Staging သို့သာ လုပ်ပါ။

## 3. Export တွင် ပါဝင်သည့် အရာများ

- Root collection အားလုံးနှင့် ၎င်းတို့၏ subcollection အားလုံး (recursive)။
- Document field အားလုံး၊ map/list/null/boolean/number/string/timestamp/reference value များ။
- Document တစ်ခုချင်းစီ၏ `createTime`, `updateTime` (မှတ်တမ်းအဖြစ်သာ)။
- Pagination (`--page-size`, default 300; 1000 အထိ)။
- `manifest.json` တွင် document count၊ collection count၊ root အလိုက် count၊
  SHA-256၊ ကန့်သတ်ချက်များ၊ warning များ။

Restore မတိုင်မီ `manifest.json` ၏ SHA-256 ကို စစ်ဆေးသည်။ မကိုက်လျှင်
ချက်ချင်း ရပ်သည် (`--skip-integrity` မသုံးသင့်ပါ)။

## 4. Export မပါဝင်သည့် အရာများ — အရေးကြီး

1. Firestore Security Rules၊ composite indexes။
2. Firebase Authentication အကောင့်များ (password, UID)။
3. Cloud Storage object များ။
4. Document `createTime`/`updateTime` ကို restore လုပ်မရပါ (Firestore က အသစ်သတ်မှတ်သည်)။
5. Point-in-time recovery မရှိပါ။ Backup နှစ်ခုကြား ဒေတာ ပျောက်နိုင်သည်။
6. Export လုပ်နေစဉ် ပြောင်းလဲမှုများကြောင့် root count နှင့် နောက်ပိုင်းဖတ်ချက်
   မတူနိုင်သည်။
7. Restore သည် merge/overwrite သာ ဖြစ်သည်; target တွင် ပိုနေသော document
   များကို ဖျက်မပေးပါ။

ထို့ကြောင့် ဤ JSON export ကို "managed Firebase backup" ဟု မခေါ်ရပါ။
ပြန်လည်ထူထောင်နိုင်မှု (recovery) အတွက် လုံလောက်သော ကိုယ်ပိုင် snapshot
အဖြစ်သာ သတ်မှတ်ပါ။

## 5. Free-only ရွေးချယ်မှုများ

| နည်းလမ်း | Free ဖြစ်ပါသလား | ကန့်သတ်ချက် |
| --- | --- | --- |
| ဤ REST JSON export | ဟုတ်သည် (Spark + service account) | ကိုယ်တိုင် လုပ်ရသည်; PITR မရှိ |
| Firebase Console managed export | Blaze + Cloud Storage လိုအပ် | Free-only မဟုတ်; မသုံးရ |
| Emulator export (`emulators:export`) | ဟုတ်သည် | Emulator ဒေတာအတွက်သာ; Production အတွက် မဟုတ် |
| Browser IndexedDB/local data | ဟုတ်သည် | Device တစ်ခုစီ၏ cache သာ; authoritative မဟုတ် |
| GitHub repository backup | မဟုတ် | Customer/payment data ကို Git ထဲ မထည့်ရ |

## 6. Backup ဖိုင် လုံခြုံရေး

- Export ဖိုင်များတွင် ဖောက်သည်အမည်၊ ဖုန်း၊ Credit balance၊ ငွေပေးချေမှု
  မှတ်တမ်းများ ပါဝင်သည်။ လူကြည့်ရန် မဟုတ်သော ဒေတာ ဖြစ်သည်။
- `chmod 700` directory နှင့် `chmod 600` ဖိုင်များ သုံးပါ။
- macOS FileVault (သို့မဟုတ် အလားတူ full-disk encryption) ဖွင့်ထားသော
  disk တွင်သာ သိမ်းပါ။
- Git၊ chat၊ email၊ public cloud link ထဲ မထည့်ပါ။
- အနည်းဆုံး copy နှစ်ခု (ကွန်ပျူတာ + external encrypted drive) ထားပါ။
- Backup တစ်ခုစီ၏ SHA-256 ကို သီးခြား မှတ်တမ်းတင်ပါ။
- Key ဖိုင်ကို အသုံးပြုပြီးတိုင်း `rm -P` ဖြင့် ဖျက်ပါ။

## 7. ပြန်လည်ထူထောင်ခြင်း (Restore) လုပ်ငန်းစဉ်

1. သီးခြား Staging Firebase project ရှိကြောင်း အတည်ပြုပါ။
2. Staging service account (datastore.user) ဖြင့် `firestore-restore.mjs` run ပါ။
3. Restore ပြီးနောက် document count ကို `manifest.json` နှင့် နှိုင်းယှဉ်ပါ။
4. App ကို Staging emulator/config ဖြင့် ဖွင့်ပြီး Owner/Cashier read ကို စမ်းပါ။
5. Sale/stock/batch/unit registry count များကို ကိုယ်တိုင် စစ်ပါ။
6. မှန်ကန်ကြောင်း အတည်ပြုပြီးမှသာ Production အရေးပေါ် recovery ကို
   Owner ခွင့်ပြုချက်ဖြင့် စဉ်းစားပါ။

## 8. လက်ရှိ အခြေအနေ (blocker)

- စစ်မှန်သော Production service account key မရှိပါ။
- Owner ခွင့်ပြုချက်ဖြင့် Production export မလုပ်ရသေးပါ။
- ထို့ကြောင့် **verified Production recovery backup မရှိသေးပါ**။
- ဤ tool သည် Emulator ပေါ်တွင် 2/2 PASS ဖြစ်သည် (round-trip + Production guard)။
  ၎င်းသည် စစ်မှန်သော Firebase project ပေါ်တွင် မစမ်းရသေးပါ။

## 9. Owner လုပ်ဆောင်ရန်

1. Firebase Console → Project settings → Service accounts → Generate new private key
   (backup အတွက်သာ; Worker key နှင့် မရောပါနှင့်)။
2. IAM တွင် `roles/datastore.user` သာ ပေးပါ။ အခြား role မပေးပါနှင့်။
3. အထက်ပါ export command ကို ကိုယ်ပိုင် terminal တွင် run ပါ။
4. Key ကို ချက်ချင်း ဖျက်ပြီး backup ဖိုင်ကို encrypted disk တွင် သိမ်းပါ။
5. Backup ရက်စွဲ၊ SHA-256 နှင့် သိမ်းထားသော တည်နေရာကို မှတ်တမ်းတင်ပါ။
6. Backup တစ်ခုကို Staging သို့ restore လုပ်ပြီး ပြန်လည်ထူထောင်နိုင်ကြောင်း
   သက်သေပြပါ။
